# 缓存操作预算与故障降级

## 本次边界（2026-09-07）

r12 的两次缓存 Redis 停机均产生约 4 秒业务尾延迟；缓存读写阶段为 2–5 秒桶，同窗口 PG operation 没有超过 1 秒样本。原因之一是缓存 I/O 和 PG 回源共用 `cacheFallbackTimeoutMs=2000`，提交后的 best-effort 缓存同步仍占用请求链路。

新增 `storage.cacheOperationTimeoutMs`，默认 **200 ms**，必须为正整数。只用于 TieredSnapshotStore 的缓存读取、批量读取、写入、批量写入、负缓存、删除、分布式回源锁的单次获取/复查/释放，包含等待缓存连接锁的时间。租约协调仍受原总等待预算限制。

PG 回源的 `cacheFallbackTimeoutMs` 默认仍为 2,000 ms，配额、熔断器和同键保护不变。PG 修复 ACK、可靠 Redis backlog/AOF、Outbox Publisher、业务 RPC 超时和重试次数不变；这是缓存**单次操作**预算，不是整个保存/RPC 的 200 ms 完成保证。批量租约释放等多次操作仍可能累计等待。本次不引入新熔断器或后台任务，不同时调整 PG 排队策略。

## 正确性与升级

- PG 写入与持久化修复目标仍在同一事务中提交。缓存超时只推迟修复，不回滚已提交写入，也不将该缓存超时作为权威提交失败返回。
- 缓存写没有得到成功结果时，不 ACK 修复任务。超时取消不保证 Redis 命令未发送或未执行；延后完成的命令仍由 revision-aware Lua 和后续修复处理，幂等键与版本规则不变。
- 缓存读取失败仍走有界 PG 回源；PG 本身不可用时仍允许返回存储错误。普通缓存的既有 TTL/SWR 语义没有升级为强一致，不宣称所有网络分区或部分写失败都不会旧读。
- 旧 JSON 配置省略新字段时使用 200 ms；若需保留原缓存等待预算，应显式将该字段设为原 `cacheFallbackTimeoutMs` 值。缩短预算可能增加慢环境中的回源和修复量，必须观察对应指标和 PG 负载。
- 带新字段的配置需要配套的新二进制；旧严格解析器会拒绝它。Rust 直接构造 `TieredSnapshotStoreConfig` 的调用方需补 `cache_operation_timeout`，或使用 `..Default::default()`。客户端 SDK、网络协议、SQL 和迁移不变。
- 本地与外部配置模板及 JSON Schema 同步声明默认值；没有部署到外网，没有修改 WoW335。

## 精准测试

1. 持有缓存连接锁，覆盖单/批量读写、负缓存、删除、提交后同步、租约获取/释放；验证使用独立 20 ms 测试预算而非 PG 的 2 秒，缓存失败不启动修复 ACK，所有阶段正常收尾。
2. 私有 PG 协议端点故意不响应：缓存预算 20 ms，但 PG 查询经过 80 ms 仍在等待，证明不会误用缓存预算取消 PG。模拟端点不执行 SQL。
3. JSON 默认值、独立覆盖、零值拒绝；Rust 零/亚毫秒预算在连接前拒绝。
4. 真实 PG/Redis 集成用例暂停缓存写入，批量提交两条记录；在 1 秒外层保护内返回，断言缓存超时、权威记录和两条修复目标均保留。先执行 UNPAUSE 再进行结果断言；恢复修复、缓存内容和重复提交回执均通过。该用例必须在专用数据库环境串行执行，不能针对线上 Redis 运行。

r13 两次缓存停机的四份游戏分片结果均健康，查询/业务传输错误均 0。相邻原始指标做差后，缓存故障相交窗口的两节点 cache_write / committed_cache_sync p99 均在 **100–250 ms** 桶，超过 1 秒样本均为 0；r12 为 2–5 秒桶。两地图 SDK connection_queue p99 均为 100–500 ms 桶，超过 1 秒样本 0；r12 两地图分别为 2–5 秒和 5–15 秒桶。SDK exchange 仍有 1/4 份超过 1 秒样本，不能宣传所有 RPC 都小于 200 ms。

分析不把两个不连续故障窗口之间的健康流量算入故障聚合；只聚合与故障开始至业务恢复相交的采样增量，边缘包含少量健康流量。本轮没有重启应用进程，未检测到直方图计数回退。桶区间不是精确分位数，父子阶段不能相加或相减。

PG 不可用仍有明显排队：12:30:24–12:31:24 主节点 PG connection_wait 均值约 5.18 秒、p99 在 15–30 秒桶，另一节点均值约 6.47 秒、p99 在 10–15 秒桶。AOF 故障涉及 PG/可靠 Redis 停机，游戏 p99 仍达约 3.07/4.46 秒。这些路径并未被本次缓存预算改动解决；下一步应单独评估 PG 排队控制，不再混同缓存操作超时。
