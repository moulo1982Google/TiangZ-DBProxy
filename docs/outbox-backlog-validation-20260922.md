# Outbox 积压方案对比（2026-09-22）

后续进展：组合两条路径的方案已通过并进入生产查询，见[后续验证](outbox-hybrid-validation-20260922.md)。以下保留早期候选的排查过程。

本轮结论：顺序与并发回归已补强，但尚未找到可以替换现有领取查询的方案。三种改写都在部分分布上退化，生产 SQL 已恢复到本轮开始时的版本，没有增加 Outbox 索引或迁移 015。不能把“测试通过”写成“积压性能问题已解决”。

## 环境与方法

沿用用户授权的 Docker PostgreSQL 18.6-bookworm、Redis 8.8.1-trixie 环境。本轮数据库查询和并发测试只连接独立 PostgreSQL 测试库，没有运行 Redis 发布往返、故障矩阵或容量压力测试。

每个分布插入 100,001 条消息，比较完整领取 UPDATE，包括排序、前序排除、跳过行锁和租约写入。每次使用保存点回滚，并实际检查返回事件。每种分布结束后事务回滚及 VACUUM ANALYZE。没有强制使用某个执行计划。下表为同一轮各一次测量，受缓存、顺序、统计抽样影响，只用于排除明显退化方案，不作为容量承诺。

## 对比结果

| 分布 | 现有查询 ms | 逐组查询第一条 ms | 先排除死信阻塞 ms | 汇总每组最早序号 ms |
| --- | ---: | ---: | ---: | ---: |
| 全部可领取，独立分组 | 96.415 | 384.282 | 169.662 | 129.982 |
| 大量延后重试 | 19.550 | 0.080 | 15.966 | 63.037 |
| 大量有效租约 | 29.155 | 9.183 | 55.885 | 75.459 |
| 1,000 组死信头阻塞后续消息 | 384.588 | 678.736 | 422.606 | 52.724 |

- 逐组查询第一条：LATERAL + LIMIT 1，仍可能对大量候选反复查索引，正常样本页面访问由 4,705 增到 402,353。没有采用。
- 先排除死信阻塞：只增加排除条件时，执行器未按预期先排除；强制把中间结果保存后，增加了扫描和中间结果成本。没有采用。
- 汇总每组最早序号：GROUP BY + MIN，明显改善死信积压，但正常领取、延后重试和有效租约场景变慢。没有采用。

候选 SQL 仅保存在 `tests/fixtures/outbox_candidate_*.sql`，由独立诊断测试读取；正式运行始终读取 `src/outbox_claim.sql`。诊断测试判断结果是否正确并输出成本，不把候选正确误认为候选性能合格，也不把这些候选加进生产路径。

## 对之前结论的修正

首次对比仍沿用“延后重试整条查询少于 100 页”的断言，发现它会失败。实际计划中 `available_at` 确实使用 ready 索引，只得到一条候选，但统计估计可能是 1,000 条，随后前序检查选择扫描 100,001 条未发布消息，总计访问约 2,338 页。问题不是日期索引缺失，而是数据分布和估计影响了后续连接计划。

不能靠禁用顺序扫描、强制索引或放宽断言来宣称问题解决。原 `query_plans` 的精确页数回归现在明确使用**所有延后消息同一重试时刻**的可重复夹具；新增 `outbox_candidate_plans` 保留每行不同重试时刻的分布和整条查询的计划证据。这两个场景必须分开解释。之前单次低页数结果不代表任意延后积压都能低成本处理。

## 已完成的保护与验证

- `outbox_concurrency` 新增四种队首状态：延后重试、有效租约、被其他事务锁住、死信。每种状态都检查同组后继不能越过队首，独立组仍能领取，未知 publisher 不能领取。
- 该套原有竞争领取、过期租约、管理员重试、原子回滚等检查与新测试共 7 项真实 PG 测试通过。
- 新诊断对比 1 项通过，四种分布 × 四种查询共 16 份完整计划和返回值检查。
- 通用查询回归 3 项另行验证。Rust 工作区 188 项、SDK 21 项通过，格式、Clippy、Actions 配置检查通过。没有改协议，不需要协议代码生成；SDK 测试按既有命令执行自己的生成及构建流程。
- CI 的索引检查任务新增单独的 Outbox 测试库，运行顺序与并发测试。独立数据库避免其他领取测试留下的消息干扰结果；远程 CI 尚未执行。

PowerShell 复测：先设置独立空库 URL 和 `DBPROXY_TEST_ALLOW_SCHEMA_MIGRATION=1`，分别使用不同测试库执行：

```powershell

cargo test -p tiangz-dbproxy-storage --test outbox_concurrency --locked -- --ignored --nocapture --test-threads=1
cargo test -p tiangz-dbproxy-storage --test query_plans --locked -- --ignored --nocapture --test-threads=1
```

本机证据在 `target/outbox-index-validation/`：最终对比 `candidates-final.log`、并发 `concurrency.log`、通用查询 `query-final.log`，以及各代码检查日志。保留了早期失败计划，没有用成功报告覆盖失败原因。

## 下一步

Outbox 性能问题仍未关闭。下一轮应比较“少量候选优先尝试，找不到再按组查找”和“单独维护每组最早未完成消息”两条路线。前者必须验证连续领取、锁竞争和坏队首长期积压；后者涉及提交、发布确认、重试和历史数据补齐的原子一致性，不能只加一张表就上线。以本轮四种分布和顺序回归作为验收起点，选出方案后再申请下一迁移号。
