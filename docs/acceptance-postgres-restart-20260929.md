# F05：普通写入和清理期间恢复原 PG 卷

使用专用 PG 容器和独立命名持久卷，分别正常停止与 SIGKILL，再启动同一容器、挂载原卷。共享测试 PG/Redis 及其他服务不停止。工作台限制 4 CPU/16 GiB，专用 PG 限制 2 CPU/3 GiB，均固定 cpuset。夹具只有 5,000 条过期回执，脚本要求宿主至少 10 GiB 空闲空间；不做真实磁盘填满。

每阶段使用新库。先写入 20 笔明确成功的业务，放入 5,000 条过期和 100 条近期回执。真实服务完成至少一批清理但仍有积压时，另一个普通写入在回执 AFTER INSERT advisory lock 屏障上等待。确认这两个条件后通知宿主停止或强杀专用 PG，停机三秒再启动。

要求未提交写入返回 StorageUnavailable，恢复后快照和回执均不存在；20 笔已确认业务内容、版本不变且原请求仍 Duplicate。结果未知请求按原 ID 重试后 Applied，再次重试 Duplicate，版本保持 1。核对 PG system_identifier 不变、postmaster 启动时间改变，证明原集群重启；既有删除不能恢复，剩余清理自动续完，近期回执保留，DP 不重启。

## 编排失败与修复

- `pg_20260929a`：PG 镜像初始化时先启动仅接受 Unix socket 的临时服务。默认 pg_isready 提前成功，工作台随即 TCP 连接被拒绝，测试未开始。修复：明确 `pg_isready -h 127.0.0.1`，等待正式 TCP 服务。
- `pg_20260929b`：工作台 root 创建了证据子目录，宿主用户无法写故障时刻文件，编排终止。修复：通过原工作台容器写入标记，保持目录所有权和权限不变。

以上轮次失败记录、停止的容器及数据卷全部保留。禁止用放宽断言、删除证据或改共享目录权限掩盖夹具错误。完整复测使用新 RunId `pg_20260929c`。

## 复测

入口：宿主执行 `bash deploy/remote-test/run_f05_restart.sh <新RunId>`，镜像默认 `dbproxy-workbench:f06-20260929`。结束时停止专用容器，保留原卷、服务日志及宿主标记；不自动删除失败数据。

`pg_20260929c` 完整复测通过，Linux 实际运行一项含正常停止/SIGKILL 两阶段的测试，耗时 140.41 秒。

原集群标识均为 `7690866873942794285`，三次 postmaster 启动时间不同，恢复挂载记录均指向 `dbproxy-f05-data-pg_20260929c`。两阶段均未重启 DP，未提交请求恢复后不存在，同 ID 重试一次应用、第二次 Duplicate。清理等待包含原有 60 秒失败退避和后续分批执行，并非连接恢复本身耗时。

范围：普通快照、已确认记录及一个确定未提交请求，清理在有积压的连续批次中。不是随机结果未知请求的大规模负载账本，也不是多记录事务的所有中间步骤。
