# 写入尖峰定位：WAL 段文件新建（2026-09-23）

结论：在服务器容器环境里，**所有 15 ms 以上的慢写都发生在 PostgreSQL 新建 WAL 段文件的时刻**。PG 默认 `wal_init_zero=on`，新建一个 16 MB 段要先整段写零再刷盘，期间所有事务提交排队，于是出现“相隔 10 ms 的几条写依次慢 40、30、20、10 ms”的阶梯。这是 PostgreSQL 的行为，不是 DBProxy 的缺陷；DBProxy 读取、同记录排序、读池、运行时都没有参与。复用旧段的切换不产生尖峰。

笔记本 T/U 两轮上百毫秒的尖峰是否同一原因，**机制吻合但未验证**：那两轮没有 WAL 采样，笔记本 PG 也没开 WAL IO 计时。笔记本另有一类整机停顿（显卡驱动重置），在杀连接第一轮 10:28:49 那簇里能看到压测程序自己晚发 60–80 ms，那一类与本结论无关。

## 做法

环境与 [容器对照](acceptance-container-server-20260923.md) 相同（服务器 2× P3600 RAID0，PG 18.6 四核八 GB，全部在容器内）。每轮一分钟、每秒 200 请求、std 定时、读池、split4、清理开启，外加：

- 只在专用测试 PG 上打开 `track_io_timing`、`track_wal_io_timing`、`log_autovacuum_min_duration=0`、`log_lock_waits`；慢语句门槛降到 5 ms。检查点与 WAL 参数保持默认，避免改变被诊断的行为。
- `deploy/remote-test/sample_host.sh`：每 100 ms 记录主机磁盘计数（md0 和两块 NVMe）、IO/CPU/内存压力、负载。
- `deploy/remote-test/run_spike_round.sh`：一条长连接每 100 ms 记录当前 WAL 文件名；前后各抓一次 `pg_stat_io`、`pg_stat_wal`、检查点统计和 WAL 目录段数。
- `tools/analyze_spikes.mjs`：把每条慢请求与同一时刻的 PG 日志、检查点、自动清理、服务端分段直方图差值、PG 会话等待、主机磁盘和压力、WAL 切换逐条对齐。

先排除了一个猜测：PG 容器“4 核”是 CPU 配额，曾怀疑每 100 ms 周期用完配额会被暂停。笔记本和服务器所有轮次的限流计数 `nr_throttled` 都是 0，排除。

## 结果

| 轮 | WAL 段数 前→后 | 新建写零的段 | 慢写 ≥15 ms | 写 P99 / 最大 | 读 P99 / 最大 |
|---|---|---:|---:|---:|---:|
| `spike_srv_a` | 14 → 14（全部复用） | 0 | 0 | 4.99 / 7.56 ms | 3.71 / 4.41 ms |
| `spike_srv_b` | 14 → 22 | 7 | 15 | 5.22 / 42.55 ms | 3.77 / 5.60 ms |
| `spike_srv_c` | 22 → 32 | 10 | 5 | 5.08 / 32.46 ms | 4.47 / 7.47 ms |

- 20 条慢写全部带 `wal_segment_switch` 标记，且每一处都有两三条 COMMIT 同时耗时 17–38 ms；PG 其他语句都正常。主机 md0 平均写延迟最高 0.8 ms，IO 压力停顿每次不到 3 ms，运行时心跳最大 1.8 ms，压测端发送迟到都在 0.25 ms 左右。
- 检查点：第二轮第一簇（03:11:57）发生在检查点开始之前；第二轮其余和第三轮全部发生在 03:12:07 开始、持续 269 秒的一次检查点期间。检查点开始后每页首次修改都要整页写入 WAL，WAL 量猛增，新段建得更快。更早的 `probe_srv_c`、`fault_blocked_srv_a`、`fault_kill_srv_a` 三轮期间没有任何检查点，同样在慢写时刻有 28–38 ms 的 COMMIT，说明不需要检查点，新建段本身就足以造成尖峰。

> **更正（2026-09-23）**：本报告初版写“PG 没有 5 ms 以上的语句，没有检查点”，那是读到了空日志。服务器 PG 日志默认权限 0600，工作台容器以普通用户运行，截取静默失败。修正权限并从完整日志补回后，结论不变而证据更直接：慢写时刻的 COMMIT 本身就慢。上表与本节已按补回日志更新；分析器补回后的输出在各轮 `spikes-recovered.log`。
- 尖峰期间采到 PG 会话在等 `IO/WalInitWrite`。
- `pg_stat_io` 的 `client backend / wal / init`：第二轮 7 次共写 126.7 ms、刷盘 65.3 ms，第三轮 10 次共写 151.4 ms、刷盘 107.3 ms，即每新建一段约 25–27 ms 的同步 IO，由正在提交的后端自己执行。第一轮没有这一行。
- 服务端分段只在 PG 写操作和取写连接等待上有 10 ms 以上的样本，读取全部正常。
- 反向核对：新建段的切换都伴随尖峰；第一轮唯一一次切换复用了旧段，没有尖峰。第二、三轮各有一次“切换无尖峰”，都是紧接前一次切换 100 ms 内的连续切换，属于同一簇。

为什么时有时无：段文件在检查点后会被回收复用。测试 PG 刚启动或者两次检查点之间 WAL 增长超过已有段池时，就要新建。第一轮开始时有 14 个可复用段，够用；后面两轮检查点还没到（默认 5 分钟），段池用完只能新建。

## 对 DBProxy 和部署的含义

- 不需要改 DBProxy 代码。尖峰只是 PG 提交变慢在写请求上的体现，数据正确、无错误、无漏发。
- 生产上同样会出现：PG 重启后、写入突然增加、或 WAL 增长超过 `min_wal_size` 保留的段池时。每新建一段让所有提交多等几十毫秒；在慢盘或虚拟磁盘上可能到上百毫秒。
- 可选的 PG 参数方向（尚未实测，需要单独 A/B）：
  - 提高 `min_wal_size`，让检查点后保留更多可复用段，稳态下基本不再新建；启动后的第一轮增长仍会发生。
  - `wal_init_zero=off`，新建段不再写零；PostgreSQL 文档主要针对写时复制文件系统推荐，ext4/xfs 上可能把代价转移到后续刷盘，必须实测。
- 验收判读：两小时运行开始阶段会出现这一类尖峰，随后随检查点回收而减少。判读时应单列“WAL 新建段”类尖峰，不能与机器停顿或 DBProxy 问题混在一起。
