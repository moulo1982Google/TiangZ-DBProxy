# F08：运行中清理索引损坏与恢复

入口：`fault_process::f08_runtime_index_damage_times_out_and_recovers`。服务先以完整索引正常启动、完成一次空清理，然后仅在新建测试库中破坏索引；没有绕过启动结构检查。

两组各用新库：

- 缺失：删除 `dbproxy_idempotency_retention`，查询目录确认不存在。
- 无效：删除原索引，以同名对有重复值的 namespace 建并发唯一索引，要求构建返回 23505，并查询 `pg_index.indisvalid=false`。这是测试造出的无效索引，不是生产迁移。

每组包含 10 万条近期回执、501 条过期回执。索引损坏不一定使这个规模的清理变慢，因此另用 AFTER DELETE 测试触发器等待 3 秒，确定性验证现有生产 2 秒 statement_timeout。超时必须记录 57014、失败计数增加一次、删除计数不增加，501 条全部回滚；不能把这次人工延迟说成索引缺失自然导致的耗时。

移除延迟触发器并恢复正确索引后，不重启 DBProxy，等待正常的 60 秒退避到期。要求 501 条继续清完、10 万条近期保留、失败计数仍为 1。故障与恢复期间每约 500ms 写一个新记录，逐笔要求成功且 revision=1，最后逐笔读取核对载荷；原请求仍为 Duplicate、原快照内容保持不变。

此项覆盖运行中结构异常、慢 SQL 上限、可观测失败、退避和修复续清；不证明任意数据量下无索引扫描的性能，也不表示服务会自动重建损坏索引。禁止去掉触发器故障说明、修改生产超时或放宽错误/一致性断言来通过验收。
