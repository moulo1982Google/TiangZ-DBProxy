## 二、环境与数据

### 固定环境

- Docker PostgreSQL `18.6-bookworm`、可靠 Redis `8.8.1-trixie`，另设同版本易失缓存 Redis。
- 可靠 Redis 开启 AOF、禁止自动淘汰；缓存 Redis 关闭 AOF/RDB，用临时数据目录。启动前读取实际配置，不能只看 Compose 文件。
- 端到端测试使用重新构建的 release DP 进程和真实 TCP SDK 请求。记录源代码摘要、二进制摘要、镜像摘要、PG 参数、CPU/内存/磁盘和 Docker 配置。
- 用户已确认并授权切换到固定性能配置：PG 容器 CPU 上限 4 核、内存上限 8 GiB、shared_buffers 2 GiB；work_mem 2 MiB、maintenance_work_mem 64 MiB、max_connections 30 继续固定。使用 docker-compose.performance.yml 叠加配置。CPU 是配额而非独占物理核心，结果只代表该 Docker 环境。此前 1 GiB 样本保留为历史证据，不与新规格结果直接混算。
- 数据使用本机 Docker 命名卷；容器显示的虚拟磁盘容量不能当作宿主可用空间，正式大规模测量前仍要核对宿主空间和实际磁盘介质。
- 多租户先用 2 个独立 PG 数据库，每租户 4 个请求连接；加队列、回执清理和测试连接，启动前核对总数小于 30。请求并发数不等于 PG 连接数。
- 普通回归、性能、故障测试分别使用独立资源。性能计时期间不得同时跑编译、其他测试或故障注入。

### 执行前必须补的工具

1. **资源隔离**：参数化数据库、Redis、容器和端口；核验容器归属后才允许停止/强杀。不能仅靠 Compose 项目名隔离，因为现有配置含固定 container_name。
2. **故障脚本改造**：已将 `tools/fault_matrix.ps1` 改为显式传入项目和三个连接地址，取消隐式清库；测试从环境读取容器名并验证 Compose 归属。使用独立缓存容器。调用者仍须核对连接地址与所选容器对应。
3. **结果账本**：负载端持久记录请求号、请求内容摘要、版本条件、响应和时间。区分明确成功、明确失败、结果未知；结束后与数据库逐条核对。
4. **进程级用例**：补真实 DP 启动、多租户后台清理、强杀 DP、恢复后的观测，不用只调用后台函数代替。
5. **性能控制器**：以固定请求速率发压，记录发送端排队和端到端耗时，避免服务变慢后发压量也下降、掩盖延迟。监测发压端资源，避免把发压机瓶颈当作 DP 瓶颈。
6. **精确故障点**：提交前、提交后响应前、回执冲突判断后、清理删除后提交前等，用测试钩子或受控代理暂停，不靠随机 sleep 猜时机。测试钩子不进入正式默认配置。

故障测试的 opt-in 缺失时，`fault_matrix` 现已直接失败，避免未注入却显示通过。验收仍须核对注入事件日志，不能只凭 test result 为 ok 判断故障执行过。

## 四、性能测试用例

### 对照方法

保留完整当前工作区后建立隔离对照构建，禁止 reset/clean 工作区。登记三个对照：B0 为本轮修改前可复现版本，各自从空库生成相同业务数据，仅作性能对照，不进行跨版本升级；B1 为当前代码但测试宿主不启动回执清理；B2 为当前完整服务。B1 的控制只能通过测试宿主或明确记录的测试开关实现，不能假称已有生产关闭配置。

索引写入成本另用两个从空库创建、业务数据相同的独立测试库，比较有无新增索引的写入开销。缺索引布局仅供受控存储夹具使用，不能直接启动当前正式服务或绕过启动检查。这是性能对照，不是旧库升级测试。

每个计时场景预热 2 分钟、采样 5 分钟，至少 3 轮；交替对照运行次序。记录全部原始数据和中位数，不挑最好的一轮。主要读写场景逐步增加并发 1、8、32、64；出现明显排队或资源饱和后，记录拐点并停止继续加压。

先用 B1 测稳定承载能力，再以其约 50%、75% 的相同请求速率比较 B1/B2。混合业务初始比例：40% 单读、20% 批量读、20% 单写、10% 批量写、5% 单事务、5% 多事务；每条请求内容、批量大小和 Outbox 效果分布固定。单项测试仍单独执行，不能只看混合平均值。

| 编号 | 场景/数据 | 重点观测与核对 |
| --- | --- | --- |
| P01 | 快照批量 1/30/64 条，多租户、多分区，冷热缓存分别测 | 完整 SQL、TCP 端到端耗时；缺失位置和跨事务可见性；不以库函数速度替代接口速度 |

### 暂定性能验收线

以下是本轮用于发现回归的**暂定门槛**，不是已达到的结果，也不是线上服务承诺：

- 数据错误、重复业务应用、串租户、错误成功响应：零容忍。
- 无故障、未饱和的固定负载下，不出现非预期业务错误或请求超时。
- B2 相对 B1：在相同负载下，吞吐下降不超过 10%，p99 增加不超过 20%。若绝对变化接近测量噪声，延长测量并同时报告绝对值，不能机械下结论。
- B1 相对 B0：新增索引写入成本单独报告；若正常读写同样超过上述回归线，必须解释并优化，不能仅用清理/领取变快抵消业务退化。
- 每批删除最多 500 条；锁冲突能在配置预算附近失败；清理 SQL 能被 2 秒数据库超时取消。客户端观测还含连接、调度和回滚开销，不能把 2 秒误当作所有网络故障下的端到端硬上限。
- 已恢复健康、未锁住的数据，在两次空闲轮询周期内能观察到清理/处理进度；清空时间按积压与实测速率估算，不对百万行规定不现实的统一秒数。
- 正常稳定负载下，当生成的到期数据速率低于实测清理能力，积压不能持续单向增长。两小时末的资源和延迟趋势不能显示未解释的持续增长。

若用户后续提供线上峰值、p99 目标、租户数和硬件规格，再追加绝对吞吐/延迟验收线；不凭笔记本样本编造线上容量。

## 五、故障注入用例

每项先跑健康基线，记录注入时刻和被影响请求，再注入、恢复、核对数据库及结果账本。关键竞争/崩溃点至少重复 3 次。不同故障串行执行。停止/强杀仅作用于已核验归属的测试进程和容器。

| 编号 | 注入方法与时机 | 恢复后必须满足 | 准备状态 |
| --- | --- | --- | --- |
| F01 | DP 已发送写请求，PG 提交前终止该数据库连接 | 未提交事务回滚；结果未知请求仍用原 ID 重试；最终不半写、不多写 | 补确定性事务屏障 |
| F02 | PG 已提交、DP 尚未把响应发给客户端时断开客户端连接 | 客户端标记结果未知；保留窗口内原 ID 重试得到原结果，不能增加版本 | 补受控响应屏障 |
| F03 | 清理已删除候选、尚未提交时终止清理连接或强杀 DP | 未提交删除全部回滚；重启后正常续清；不影响其他表 | 补精确清理屏障 |
| F04 | 清理提交后、记录计数/日志前强杀 DP | 已删回执不恢复，业务数据不变；允许进程内监控少记本次，但不能据此重复业务写 | 补进程故障点 |
| F05 | 普通写入和清理并行时停止/强杀 PG，再恢复原卷 | 没有收到明确成功的未落库请求；结果未知按原 ID核对；已确认的持久数据恢复；清理重新开始 | 已有 PG 故障部分；补清理并发 |
| F06 | 保持 TCP 连接但阻断/延迟 PG 流量，再恢复 | 连接/执行超时边界可解释；无无限积压或重连风暴；不将维护失败误报为业务成功 | 补隔离网络代理 |
| F07 | 锁住一部分过期回执，再锁整张回执表 | 行锁被跳过；表锁等待超时、回滚、延后重试；释放后恢复，近期回执不误删 | 已有库级；补实际后台节奏 |
| F08 | 删失清理索引后重启；运行中索引失效另测 | 启动必须拒绝；运行中不能无限占用 PG，应超时并可观测；恢复索引后继续 | 已有启动漂移；补运行中场景 |
| F09 | PG 连接额度受限或拒绝新连接 | 明确启动/重连失败，不能静默降级内存；已有业务受影响程度有记录；恢复后可重连 | 补 |
| F10 | PG 测试专用受限磁盘满、只读或日志写入失败 | 不错误确认持久写入；事务无半提交；恢复后按结果账本核对和续清 | 补受限存储夹具；不得填满宿主真实磁盘 |
| F11 | 停止/强杀可靠 Redis，覆盖 backlog 已持久确认与未确认两类 | 已持久确认队列数据可恢复；未确认不伪报成功；恢复后排空且版本正确；普通回执清理仍可运行 | 已有 7 项旧故障中有覆盖；补清理并发 |
| F12 | 强杀易失缓存 Redis，在 PG 更新后恢复 | 不恢复旧缓存并返回已确认之前的版本；权威读取正确；缓存修复可恢复 | 已有；需启用独立缓存容器 |
| F13 | Outbox 已发布到 Redis、PG 确认前终止进程；有效租约及过期重领交错 | 允许消息重复投递，消费者按 event_id 去重；业务不能重复；同组顺序不被破坏，旧租约不能确认新租约 | 已有租约/发布部分；补进程崩溃整链路 |
| F15 | 租户 A 的连接/清理故障，B 持续正常流量；监控服务短时不可用另测 | 不串库、不清错数据；故障有租户归属；监控不可用不能阻止数据库正确提交 | 补真实双租户故障 |

需要特别区分：网络断开不等于数据库一定没提交；没有响应不等于明确失败；Outbox 发布是允许重复投递的恢复模型。测试报告不得把这些状态混为一谈。
