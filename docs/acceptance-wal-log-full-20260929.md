# F10：受限 WAL 满与日志写入失败

2026-09-29，220 专用容器。`wal_20260929b` 和 `log_20260929b` 通过；正式 release DP 全程未重启。生产代码未修改。

## 隔离与故障证据

- 专用 PG 18.6：2 CPU、3 GiB 内存；工作容器 4 CPU、16 GiB；固定 CPU 集合。共享 PG/Redis 不停机。
- PGDATA 使用新命名数据卷；WAL 独立 128 MiB tmpfs，日志独立 8 MiB tmpfs。填充前验证最终目录文件系统类型确为 tmpfs，并保存挂载与卷配置。只删除本轮明确创建的 ballast 文件，未填充宿主真实磁盘。
- WAL 满后通过实际写入和 WAL 切换触发 `PANIC: could not write to file "pg_wal/xlogtemp.122": No space left on device`，再释放空间并重启原 PG。恢复前后的 `system_identifier` 相同。
- 日志满通过 64 KiB `RAISE LOG` 和尾标记缺失证明写不完整，不能仅凭 `df` 为零就断言所有追加都失败。恢复空间后新的日志标记确实写入。日志故障未重启 PG。

| 故障前已确认普通写入 | 20 | 20 |

| 故障期间双记录提交获确认 | 否 | 是 |
| 重试前该事务实际记录数 | 0 | 2 |
| 最终逐条内容与 revision=1 核对 | 32 | 32 |
| 回执清理完成 | 10,000 | 10,000 |

恢复后先核对所有已经返回成功的写入，再重试未知请求，避免重试掩盖已确认数据丢失。双记录事务在重试前必须是 0 或 2 条；原操作号重试后两条内容一致，再次提交必须 Duplicate。普通写入均保留原请求号。

日志写入失败与 WAL 持久化失败是不同路径：本轮日志满时业务仍正常提交，直接 PG 核对证明没有虚假成功；不能把“日志未写入”错误解释为“业务一定未提交”。本轮普通及双记录事务覆盖不代表所有磁盘、控制器或主机掉电故障形态。

## 轮次与修复

- `wal_20260929a` 初版普通写入检查通过（140.02 秒），随后加入双记录事务无半提交检查，使用全新 `wal_20260929b` 重跑通过。
- `log_20260929a` 夹具错误：要求日志文件大小不变，实际上已分配末尾块仍可追加，文件从 1,847 增到 2,116 字节。脚本判错后停止本轮容器，未形成通过结论。修正为超过末尾块空间的 64 KiB 消息，检查增量不足整条长度、尾标记缺失，以及释放空间后的新标记落盘。没有改产品、放宽业务一致性断言或覆盖失败证据。
