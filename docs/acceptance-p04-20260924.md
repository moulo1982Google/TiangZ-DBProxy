# P04：100 万条回执同时到期（2026-09-24）

结论：**通过（`p04_b`）。** 每秒 200 请求下，100 万条同时到期的回执在约 34 分钟内清完，速度约每秒 490 条，正好是默认节奏（满批 500 条、停 1 秒）的上限。清理期间和清完以后，读写 P50 / P99 几乎一样：读 P99 4.30 对 4.37 ms，写 P99 5.20 对 5.08 ms。全程 54 万次请求零错误、零漏发，27.1 万次写入全部核对一致，100 万条近期回执一条不少。

第一轮 `p04_a` 因为漏传核对时限，被判失败，保留在下文。它的清理数据与 `p04_b` 一致。

## 做法

- 环境：服务器容器（同 [P08](acceptance-p08-2h-20260923.md)），PG 18.6 四核八 GB。全部生产后台任务开启，回执保留 24 小时，清理开启。
- 预置：100 万条已过期回执（169 小时前）和 100 万条近期回执，按模板库克隆出本轮全新数据库。
- 负载：每秒 200 请求，读写各半，32 在途，std 定时，读池 4 写 + 2 读，SDK split4；预热 10 秒，测量 2,700 秒。
- 观测：
  - 每 30 秒一次 PG 状态，其中包括“待清理的过期回执数”，用保留期索引按范围计数。
  - 每 0.1 秒一次 WAL 位置。
  - 主机与容器资源采样。
  - PG 日志记录超过 5 ms 的语句。
- 分析：`tools/analyze_p04.mjs` 先找到积压清零的时刻，再把请求延迟分成“清理期间”和“清完以后”两段对比。
- 入口：`deploy/remote-test/launch_long.sh <run-id> 2700 <redis-db> --fixture-expired 1000000 --fixture-recent 1000000 --reconcile-budget 900`。

## `p04_a`：判为失败（核对时限不够），清理数据完整

- 启动时漏传核对时限，用了默认的 180 秒。压测本身完整跑完：54.2 万次请求零错误、零漏发。
- 核对 27.1 万次写入时，查到第 257,729 次时时限到了，整轮判为失败。已核对的部分零差异。这一轮保留，用 `--reconcile-budget 900` 重跑为 `p04_b`。
- 清理数据：
  - 第一次采样时（负载开始后约 28 秒）积压 985,500 条。约 1,963–1,993 秒后清零，从负载开始算不超过 2,021 秒。
  - 平均每秒约 495 条，正好是默认节奏的上限：满批 500 条后停 1 秒，每批本身约 4–5 ms。
- 清理期间和清完以后的延迟对比（`load.out` 的时间作为负载开始时间，误差约 ±1 秒）：

| 时段 | 读 P50 / P99 / P99.9 / 最大 | 写 P50 / P99 / P99.9 / 最大 | 错误 / 漏发 |
|---|---|---|---:|
| 清理期间（约 33.5 分钟） | 3.59 / 4.09 / 5.06 / 15.5 ms | 4.48 / 5.17 / 5.99 / 66.7 ms | 0 / 0 |
| 清完以后（约 11.5 分钟） | 3.59 / 4.47 / 4.85 / 8.2 ms | 4.48 / 5.10 / 5.79 / 7.8 ms | 0 / 0 |

- 两段的 P50 和 P99 基本一样，清理没有可测出的影响。
- 清理期间写入最慢的 66.7 ms，以及同一时刻 22–48 ms 的慢 COMMIT，都集中在负载开始后约 28–30 秒。当时 PG 每 0.5 秒就切换一个 WAL 段，持续约 6 秒，结束时间与**模板库** `p04_a_base` 的自动清理（autovacuum）结束时间完全一致（01:59:27.27）。所以这是准备 200 万条测试数据的副作用，与回执清理无关。除此之外，整轮 54 万次请求中超过 10 ms 的只有 14 次，最慢 15.5 ms。
- PG 日志里超过 20 ms 的语句，除上述 COMMIT 外，都是本测试自己的 30 秒采样查询（每次约 170–240 ms，主要花在给 100 万条积压计数）。
- 表空间：回执表从约 437 MB 增长到 684 MB（新写入 27 万条，删除 100 万条）。删除留下的空间要靠自动清理回收，期间自动清理跑了 3 次，死行降到 9 万条。

## `p04_b`：通过

- 核对时限 900 秒。压测完整跑完，全部 271,000 次写入核对零差异。
- 清理：
  - 第一次采样时（负载开始后约 28 秒）积压 986,000 条，约 1,993–2,023 秒后清零，从负载开始算不超过 2,050 秒，平均每秒约 487 条。
  - 结束时删除计数正好 1,000,000，待清理为 0；近期回执全部保留（活行约 127 万 = 100 万近期 + 27 万新写入）。

| 时段 | 读 P50 / P99 / P99.9 / 最大 | 写 P50 / P99 / P99.9 / 最大 | 错误 / 漏发 |
|---|---|---|---:|
| 清理期间（约 34 分钟） | 3.61 / 4.30 / 5.09 / 18.4 ms | 4.45 / 5.20 / 6.47 / 65.9 ms | 0 / 0 |
| 清完以后（约 11 分钟） | 3.61 / 4.37 / 4.77 / 6.2 ms | 4.45 / 5.08 / 5.94 / 10.6 ms | 0 / 0 |

- 与 `p04_a` 一样：负载开始后 28–34 秒，PG 连续切换了 15 个 WAL 段，同时出现 22–60 ms 的慢 COMMIT。这段时间与模板库 `p04_b_base` 的自动清理（02:49:33–02:49:41）重合，清理期间的最大值（写 65.9 ms、读 18.4 ms）都出在这里。
- 这 6 秒以外，整轮超过 10 ms 的请求只有 6 次，最慢 12.1 ms。PG 日志里另外只有 5 条慢 COMMIT，时间在 03:14–03:21，都是检查点期间。
- 负载开始约 1 分钟后，出现过一次因 WAL 量触发的检查点（`checkpoint starting: wal`），原因是建库和模板清理产生了大量 WAL。之后都是每 5 分钟一次的定时检查点。
- 表空间：回执表从约 437 MB 增长到 683 MB，自动清理跑了 3 次，结束时死行 8.7 万。

## 与计划的差异与边界

- 计划写的是“随后新旧各半、不同重试时刻”。这里新写入的回执随负载持续产生，但没有专门安排“同一请求号在清理前后不同时刻重试”的请求。
- 清理速度由固定节奏决定（满批停 1 秒），所以 100 万条积压要约 33 分钟。如果需要更快，要调节奏或批量，这属于设计决定，本轮不改。
- 单实例单租户，服务器容器环境。
