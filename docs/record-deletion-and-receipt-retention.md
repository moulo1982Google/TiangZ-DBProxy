# 普通回执保留期与记录删除边界

> **2026-09-23 变更**：保留期从写死的 7 天改为配置项 `storage.receiptRetentionHours`，**默认 24 小时，取值 1–8760 小时**（下限 1 小时，上限一年只防误配）。清理语句改为绑定参数，不再写死 168 小时。理由与测算见“保留期如何选择”一节。下文 2026-09-22 的验证数字是在 168 小时规则下得到的历史证据，机制不变。

2026-09-22：已实现 PostgreSQL 普通快照回执清理，迁移 **015 receipt-retention**。只清理 `dbproxy_idempotency`，不删除快照记录，不清理单记录事务、多记录事务及其 records、交易回执、账本、追加事实、Outbox 或 operation_claims。本轮不新增记录删除接口。

## 对调用方的约定

- 普通回执至少保留配置的时长（默认 24 小时）。计时使用 PostgreSQL 首次插入回执语句的时间 `recorded_at`，不使用业务传来的 `updated_at_unix_ms`，也不因重试而续期。
- 恰好到达保留时长不清理，只有严格早于截止时间才进入清理。后台停机、积压或行锁可能让回执保留更久，因此这不是精确到秒的删除期限。
- 保留期间，重试仍必须使用原请求号和相同内容。事务回执的规则没有改变。
- **普通回执被清理后，同一个请求号可能被当作新请求处理。** 带 expected_revision 的写入仍受版本检查保护，可能返回版本冲突；不带版本检查的旧请求可能再次写入并增加 revision。调用方不能把普通回执当成永久去重或永久业务凭证，也不能把“清掉回执”理解为撤销原来的写入。
- SaveSnapshot、SaveMultiSnapshot 中的普通保存，以及普通排队保存最终落库的回执使用这张表。Redis backlog 的持久 fence 和快照数据不会随回执删除。MemoryBackend 没有数据库清理任务，不是这套磁盘保留策略的实现。

## 时间与索引

迁移 015 新增 `recorded_at TIMESTAMPTZ NOT NULL DEFAULT statement_timestamp()`，并建立 `(recorded_at, request_id)` 索引。稳定默认值给旧回执统一赋予迁移时刻，升级后旧数据仍有完整一个保留期的宽限，不拿旧业务时间批量判断过期。索引加入启动结构检查和只读巡检。

迁移沿用已有事务迁移机制。建索引需要扫描旧表，并可能阻塞写入；大库必须安排维护窗口。新增索引也有磁盘和写入维护成本，不能称为零成本。当前检查覆盖 18 张表主键、17 项辅助索引和 32 个快照分区主键。

## 后台清理

正式 PG 服务在每个进程内为每个租户数据库增加一条独立清理连接和一个后台任务，不占用请求分片或现有队列连接。部署连接预算按“每实例每租户一条”累加：两个实例连接同一租户库时就有两条清理连接、两个清理任务同时运行。多个任务靠行锁跳过彼此正在删除的行，不会重复删除或互相阻塞，但删除速率和连接数会随实例数放大；目前没有只允许一个实例清理的开关。直接使用存储库的宿主需自行调用 cleanup_expired_receipts；仅 connect/connect_existing 不会启动后台任务。服务启动后执行第一批：

- 按时间索引取最老的最多 500 条过期回执，使用行锁并跳过正在被其他事务锁定的行。
- 在同一条 SQL 中，按这些已锁定行的临时物理位置直接删除；行位置不持久化，也不跨语句复用。
- 满批后暂停 1 秒再执行下一批；不足一批、没有过期数据或失败时，暂停 60 秒。
- 清理事务的 SQL 超时为 2 秒，表锁等待上限 100 毫秒。失败回滚，并延后重试。停机信号可以打断空闲等待；执行中的批次先完成或超时，仍受服务已有停机宽限期控制。
- 500 是删除数量上限，不是索引访问次数的严格上限；大量被锁回执可能增加查找成本，因此同时设置数据库执行超时。

删除只是移除回执，空间由 PostgreSQL 自动清理机制回收用于复用，不保证数据库文件立即缩小。后台不运行 VACUUM FULL，不自动删除历史分区。

监控端点新增累计批次数 `dbproxy_receipt_cleanup_batches_total`、删除条数 `dbproxy_receipt_cleanup_deleted_total`、失败次数 `dbproxy_receipt_cleanup_failures_total`。成功删除记录条数和耗时日志，失败记录原因；不为监控周期性 COUNT 整张回执表。进程重启会重置这些进程内累计值。

## 并发重试

原来的“发现请求号冲突，再读取回执”之间存在清理竞争窗口。本轮修正为：读到回执后持有键共享锁到事务结束，防止清理删除；如果清理先删除了回执，则重新尝试声明请求号，按保留期之外的新请求处理。普通写入和回执仍在同一事务提交。

测试使用独立库中的语句触发器，精确暂停在冲突判断与读取之间，再运行清理并恢复重试，确认不会因回执消失报空行错误。测试触发器不进入生产迁移。

### 捕获并修正的执行计划问题

初版用 request_id 连接候选表删除。即使候选 LIMIT 500，PG 仍可能选用连接计划扫描整个回执表；十万条近期数据回归因此失败。正式版本改为同一条语句内按已锁定行的位置删除，最终计划为保留期索引范围扫描加 Tid Scan，没有 Seq Scan。测试继续断言使用清理索引且没有全表扫描，没有靠禁用顺序扫描或删除断言绕过失败。

在 100,000 条近期、601 条过期样本中，正式方法三轮分别删除 500、101、0 条，近期回执全部保留。单次解释执行约 0.5 毫秒、共享页访问约 1,604 次；包含行锁和删除成本，共享访问不等于物理磁盘读取，也不是容量承诺。

证据保存在 `target/receipt-retention-validation/`：首次失败 `retention.log`，最终存储 `retention-final.log`，后台任务 `worker.log`，其余回归与代码检查各有日志。日常 CI 加入存储保留期测试，发布真实环境检查加入后台任务测试。

复测命令（独立空库、迁移授权标记、串行执行）：

```powershell
cargo test -p tiangz-dbproxy-storage --test receipt_retention --locked -- --ignored --nocapture --test-threads=1
cargo test -p tiangz-dbproxy-server --test receipt_cleanup_worker --locked -- --ignored --nocapture --test-threads=1
```

两套使用不同的 `DBPROXY_TEST_POSTGRES_URL`，并设置 `DBPROXY_TEST_ALLOW_SCHEMA_MIGRATION=1`；服务测试另需 `DBPROXY_REDIS_URL`。不要指向业务数据库：升级测试会暂时移除 015 的字段、索引和迁移登记，以验证旧库路径。

## 保留期如何选择（2026-09-23）

回执只服务一件事：调用方不确定上次是否写成功时，用同一请求号重发，DBProxy 凭回执回答“已写过”。保留期只需盖住调用方最晚可能重发的时刻，再加余量。

- TiangZ 主工程 `VersionedEntityRepository` 对存储暂不可用最多重试 3 次、退避上限 200 ms；SDK 在断线时自动重连重发一次，单次请求超时 5 秒。实际重发窗口是秒级到几十秒。
- 请求号带进程启动时间戳，进程重启后不会用旧请求号重发旧数据。
- 所有 Repository 保存都带期望版本号；回执删除后若仍有极迟的重发，会得到版本冲突，而不是重复写入。
- 关键经济操作走事务回执，不受本规则影响。

所以对现有调用方，几十分钟即足够正确性；默认取 24 小时是给其他 SDK 调用方、运维手工重跑和事后查询“这笔是否写成”留余量。业界例子：Stripe 幂等键至少保留 24 小时；AWS SQS FIFO 的去重窗口是 5 分钟。

**存储代价**：两小时实测（`acceptance-p08-2h-20260923.md`）每条普通回执约 1.5 KB（含一份完整写入内容和索引）。按每秒 100 次普通写估算：7 天约 90 GB，24 小时约 13 GB，1 小时约 0.5 GB。

**调整方法**：在配置 `storage` 段设置 `receiptRetentionHours`，重启生效；越界时启动前报错。多个实例连接同一租户库时应配置相同值，否则较短者决定实际删除时间。缩短保留期不会删除事务回执或业务数据，但会让“回执过期后同号重发按新请求处理”的窗口提前，调用方最晚重发时间必须短于配置值。
