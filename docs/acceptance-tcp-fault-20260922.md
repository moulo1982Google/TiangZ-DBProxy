# SDK/TCP 慢写与断连接验证（2026-09-22）

四项真实 PG/Redis 集成测试通过。新增用例连续三轮验证请求进行中断开 PG 连接，以及保持原 SDK 连接池继续请求、重试和去重。没有修改 DP 服务实现或协议；未开始两小时验收，也未把先前未复现的自然尖峰标为已解决。

## 本轮实际覆盖

测试文件为 `crates/dbproxy-server/tests/read_write_contention.rs`。DP 在 Rust 测试进程中启动真实 TCP 监听，客户端使用真实 Rust SDK；PG 18.6、Redis 8.8.1 使用既有 Docker 环境。不是假存储，但也不是独立部署进程的重启测试。

| 用例 | 注入与检查 | 结果 |
|---|---|---|
| 共享 PG 连接基线 | 卡住写入，验证相同 PG 分片的另一条记录读取会等；独立 PG 读取正常 | 通过 |
| 8 条 SDK TCP 连接基线 | 共用/读写拆分 TCP 各重复 3 次，验证只有 TCP 拆分仍不能隔离相同 PG 写分片等待 | 6 轮通过 |
| 正式 PG 读池 | 同样卡住写入，读取、批量读取、冷缓存回源及回执查询在放行写入前完成 | 6 轮通过 |
| 新增请求中断恢复 | 正式 4 写 + 2 读池，SDK split4，按下面步骤连续重复 | 3 轮通过 |

新增用例每轮执行：

1. 插入一条种子记录，再通过触发器中的 PG advisory lock 卡住另一条普通写入；查询 `pg_stat_activity` 确认写请求确实到达 PG 并在等待。
2. 在写入仍未完成时，经原 SDK 完成 20 次无关记录读取，逐次核对内容与版本。每次读取有 1 秒上限；这是一项隔离性验证，不是毫秒性能验收。
3. 精确终止该写入的 PG 后端 PID，确认原请求返回错误。放开锁，确认没有留下快照或普通回执。
4. 用完全相同的请求号和内容重试，得到 Applied、版本 1；再重放得到 Duplicate、版本仍为 1。
5. 暂时锁住快照表，让一条真实权威读取在 PG 内等待；确认等待状态后终止其后端 PID。原读取返回错误，没有返回缓存成功。解除表锁，原 SDK 继续读取成功，连续读取以复用读池槽位。
6. 终止该专用库除控制连接之外的全部客户端 PG 连接。三轮分别终止 8 / 5 / 5 条；后两轮未使用的写分片和维护连接按需重连，因此不要求始终保持 8 条。
7. 等待 100 ms 让断开通知传播，然后用原 SDK 连续读取、重放原写入，核对版本 1、内容正确、对应回执恰好 1 条。没有重新创建 SDK 连接池，也没有显式调用存储重连。

新增用例总预算 45 秒；整个四用例实测执行约 5.17 秒。故障中的预期错误是断连接测试断言的一部分，没有算作正常负载测试的成功响应。

## 安全边界与未覆盖项

- 本次专用库为 `tcp_fault_20260922a`；运行前确认 Docker 项目归属并新建空库，无旧库升级、无删库或 Redis FLUSH。
- 新用例要求 `DBPROXY_FAULT_DATABASE` 与实际数据库名完全一致，且名以 `tcp_fault_` 开头。杀连接查询始终限定当前库，排除控制连接，并限制客户端后端；不会终止其他库连接或重启整个 PG。
- 慢写来自确定性事务锁，**不模拟磁盘变慢或 WAL 刷盘卡顿**。
- 写入中断发生在事务提交之前，验证回滚和同号重试；**尚未覆盖“已提交但响应丢失”的不确定结果窗口**。
- 全连接中断后的断言覆盖前台读写恢复；不能据此声称后台维护连接及所有 worker 已恢复。
- 没有在每秒 200 次持续混合请求下同时注入故障，没有测试整个 PG/Redis 服务重启，也不是生产进程崩溃恢复验收。旧 T/U 自然尖峰仍未定位完成。

必须使用已授权且归属明确的独立测试 PG/Redis，以及一个全新的 `tcp_fault_...` 数据库。设置：

```powershell
$env:DBPROXY_TEST_ALLOW_SCHEMA_MIGRATION='1'
$env:DBPROXY_TEST_POSTGRES_URL='<专用新库连接串>'
$env:DBPROXY_FAULT_DATABASE='<与连接串一致的 tcp_fault_... 库名>'
$env:DBPROXY_REDIS_URL='<已授权测试 Redis 逻辑库连接串>'
cargo test -p tiangz-dbproxy-server --test read_write_contention --locked -- --ignored --test-threads=1 --nocapture
```
