# 云上 2C4G / 100 玩家混合负载实测

2026-10-01 用户授权在已有云机试验 2C4G、100 人 DBProxy 负载，同时保留教练直聘和绯红之境。首轮 300 秒预检与 900 秒主测已完成：客户端一致性与请求检查通过，但 Outbox 持续积压，容量结论不通过。用户随后要求先修改再复跑，改进版正在构建验证；不继承退役旧版或修改前制品的 24 小时资格。

## 资源与制品身份

使用独立 PostgreSQL 数据库、两个 Redis、两个 DBProxy 节点，以及全新的容器名、数据卷、网络、端口和部署目录；两个现有业务的配置、数据卷及进程保持。

- 服务端 `0.7.0-rc.2`，源码 `42f2762f99ababbe20f121e120a1ab7e2ce960da`；Linux ELF SHA256 `aa7041382667ef72cf54a7e76d23b9a19125c9475dcaa8255165789e04a6564c`。
- 负载源码 `e9596d11fecf8eec6dc181bddeacc16ccf8dd897`，冻结负载 ELF SHA256 `5d1a2b8afc8493e94920f38e18784f9e6eda7eeacbf5d433d9bc8a33025a8962`；与现有 R11 的受测字节相同，兼容旧客户端，不在云机编译。
- 受测两个 DBProxy、PostgreSQL、可靠 Redis、易失缓存 Redis **合计**使用同一 cgroup v2：`cpu.max=200000 100000`、`cpuset.cpus.effective=2-3`、`memory.max=4294967296`、`memory.swap.max=0`。父组额度包含实际归属于它的数据库页缓存，不能仅限制 DBProxy 后把存储算作免费资源。
- 负载和观察控制器另用两个 vCPU 上的 50% CPU/512 MiB 配额。此试验是在四 vCPU 共享宿主上的隔离模拟，不是独立 2C4G 虚拟机；共享磁盘、内核和已有业务仍可影响结果。
- PostgreSQL 保持 `fsync=on`、`synchronous_commit=on`、`full_page_writes=on`，512 MiB shared buffers、15 分钟 checkpoint；可靠 Redis 为 AOF/everysec，入队等待实际 AOF 确认。PG 排队 2000 ms、入队 AOF 2000 ms/总预算 4500 ms、Outbox AOF 2000 ms/总预算 5000 ms、客户端 5000 ms，未放宽。
- 每节点沿用 4 个请求分片、2 个 Tokio 线程及三个后台 worker；客户端仍先用主端点，另一个用于 failover，不能假定 RPC 均匀分配。

## 负载与测量口径

先执行完整 300 秒预检，正式计时前预置与预热完成；通过原客户端终态、一致性及零健康错误检查后，自动执行新的完整 900 秒负载。两次均为 100 名模拟玩家、1 秒循环，读取连接池 24、写连接池 8、每 10 个循环事务一次、每 30 个循环交易一次，每 5 秒一批 100 条排队写。相同幂等 ID/载荷及原始默认确认语义保持，不注入故障。

负载中的 payload 是现有探针的轻量 DTO，不代表完整游戏存档。100 人是 100 个并发玩家循环，不能解释为 100 次请求/秒；排队写成功计数是记录条数，批量 RPC 是另一个计数。客户端总数/吞吐只使用正式计时报告，服务端 RPC 直方图按观测窗口的累计差计算，P95/P99 报告有限桶的上界，不伪装为精确客户端延迟。进程与存储阶段统计包含失败/取消时不得当作成功 SQL 执行时长；共享队列的两个节点 gauge 不能相加。

控制器每约 5 秒记录父 cgroup CPU/限流、内存/峰值/OOM、宿主可用内存/磁盘及两个节点原始 metrics，约 15 秒检查保护容器/服务身份及两个页面/教练 API 健康。宿主可用内存低于 1.5 GiB、可用磁盘低于 15 GiB、保护业务异常或测试 OOM 时失败并停止本次自有资源。控制器使用独立 systemd service，不依赖本机 SSH 生命周期，最多运行 40 分钟；成功或失败收尾停止两个节点和三个存储，不启用开机自动重跑。

## 准备阶段的配置与取证问题

初次组装配置误将 `publishTimeoutMs`、`aofAckTimeoutMs`、`redisResponseTimeoutMs` 写入 `outbox` worker 分组。服务端 `deny_unknown_fields` 按真实契约拒绝启动，第一节点 readiness 等待超时，负载尚未启动；这是测试部署错误，不是框架负载缺陷。正确位置为 `outboxRelay`；保留原始错误日志和两份初始 JSON/计划，修正分组后重新校验配置 SHA、二进制/进程 SHA、父 cgroup 和 `/ready`，才启动正式计时。禁止关闭未知字段校验、调大超时或用错误配置的等待时间累计负载。

查询/下载时还出现数次 SSH 握手 `Connection closed`；原因未确认，不能据此宣称 DBProxy 故障或健康。通过独立控制器及单个持久只读 SSH 观察会话接续，保存实际应用/进程和原始区间检查，未修改 SSH/Docker/业务全局配置。

本机接续目录是相邻引擎 worktree 的 `temp/v0.7-remote-2c4g-100-20261001/`。`status.py`/`watch.py` 仅读取当前测试状态，`deploy.py`、`prepare.mjs` 和修正后的启动是一次性操作，不作为日常状态命令再运行；原配置错误、远端实际运行计划和所有输入 SHA 均须与结果一起留存。

## 内存增长的证据与边界

约 20 分钟总内存 183.09 → 335.79 MiB，增加 152.70 MiB。`memory.stat` 中匿名内存 47.23 → 71.19 MiB，文件缓存（扣除 shmem）80.79 → 174.13 MiB，共享内存 41.42 → 71.67 MiB，kernel 13.19 → 17.48 MiB。文件与共享内存占增长约八成；后十分钟匿名内存接近 70–72 MiB，不能据此证明每个 Rust/Redis 进程都无泄漏。`file` 包含 `shmem`，不得重复相加；分类统计与 `memory.current` 可能有采样/计账时差。没有 `pgscan/pgsteal`，此次并未实证内存压力下的回收。PG 配置的 512 MiB shared buffers 会按访问逐步驻留，交易/回执/Outbox/WAL 和 Stream 历史也在增长；20 分钟既不是平台期证明，也不能直接线性外推整机必定爆内存。

改进复跑增加各直属子 cgroup 的 CPU、anon/file/shmem/kernel 和进程 RSS/PSS，负载停止后保留服务 300 秒继续采样；不重启服务、全局 drop caches、裁剪未确认事件或删除事实来伪造内存下降。首轮没有子组逐项证据，无法倒填。

## 改进与复跑

用户要求先改再跑。最小修复见[Outbox 有界批量发布](outbox-batch-publication.md)：默认一轮最多 16 个独立排序组的头部，同一 Publisher/受控 Redis 连接上 pipeline XADD 后一次 WAITAOF，再逐租约 ACK。保持默认 worker 数、AOF/Redis/发布/客户端预算、至少一次及原事件 ID；无协议/迁移变更。改进版需要重新构建及制品 SHA 校验，使用新的数据库/卷与完整同样的 300+900 秒负载；增加明确的 Outbox 积压/年龄及负载后排空检查，不能改写首轮失败。改进复测尚待完成，不作 24 小时、故障或大 payload 资格声明。

本轮同时按用户指令清理本机两个无容器引用的 v7 Native 镜像，镜像总数 27 → 25；79 个容器和 46 个卷保持，未强制删除、全局 prune 或压缩 Docker VHD。标签显示字节含共享层，实际 Docker image 统计仅约减少 50 MB；构建缓存另有保留，当前验证镜像用于 Linux 重建。镜像本身不占 CPU，运行中的容器才占；未把删镜像解释为 CPU 已释放。

基线未改产品、无 codegen 或重编。后续改进不修改协议/生成源或放宽预算；未 push 或发布。
