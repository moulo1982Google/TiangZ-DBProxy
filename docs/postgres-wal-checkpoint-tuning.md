# PostgreSQL WAL 与检查点参数：对 DBProxy 的影响与建议

结论：`max_wal_size` 等 WAL/检查点参数**不影响正确性，对平均延迟和 P99 也基本没有影响**，只影响最慢的那一小撮写入（几十毫秒级的偶发慢写）。它属于部署调优，不是必须立即处理的问题。选用云 PostgreSQL 时，存储档位（IOPS/吞吐）的影响往往比这个参数更大。

本文依据 2026-09-23 服务器容器环境的实测：[写入尖峰定位](acceptance-spike-localization-20260923.md)与 [P08 两小时第二轮](acceptance-p08-2h-20260923.md)。

## 机制

- PostgreSQL 把每次提交先写入 WAL（预写日志），WAL 按 16 MB 一段存放。
- 检查点把内存里的脏页写回数据文件。触发条件有两个：距上次检查点超过 `checkpoint_timeout`（默认 5 分钟），或者这段时间写的 WAL 超过约 `max_wal_size / (1 + checkpoint_completion_target)`。按默认 `max_wal_size=1GB`、`checkpoint_completion_target=0.9`，约 540 MB 就会提前触发。
- 检查点开始后，每个数据页第一次被修改都要把整页写进 WAL，所以 WAL 量会猛增。
- WAL 段用完又没有可复用的旧段时，要新建段文件。默认 `wal_init_zero=on`，新建时先写 16 MB 的零再刷盘。这期间所有提交排队。
- `min_wal_size`（默认 80 MB）决定检查点后至少保留多少旧段给后面复用。保留得越多，需要新建段的次数越少。

DBProxy 的普通保存、事务保存都是一次 PostgreSQL 提交，所以会直接感受到上面这些停顿。表现是几条写依次变慢，比如 40、30、20、10 ms，然后一起放行。读取走读池，不受影响。

## 实测数据（200 请求/秒，其中每秒 100 次 1 KiB 写，两小时）

| 项 | 数值 |
|---|---|
| WAL 平均写入速度 | 约 0.9 MB/秒（两小时 6.5 GB） |
| 每 5 分钟 WAL 量 | 中位 193 MB，最多 923 MB；30 秒内峰值约 23 MB/秒 |
| 检查点 | 25 次按时间触发，2 次因 WAL 超过 `max_wal_size` 提前触发 |
| 15 ms 以上慢写 | 52 次，占写入 0.007%，最慢 48 ms |
| 写入 P99 | 5.2 ms，不受影响 |

- WAL 量不均匀。后台自动清理和检查点后的整页写入会形成突发，突发时 5 分钟内超过了 540 MB 的门槛。
- 52 次慢写全部落在检查点期间，并伴随 WAL 段切换和 COMMIT 变慢。其中两段紧跟在因 WAL 写满而提前触发的检查点之后。
- 开头一小时零慢写，因为数据目录里已有 64 个可复用的 WAL 段。
- 更早的一分钟短测中，没有检查点时也出现过同样形态的慢写，原因是新建 WAL 段。

调大 `max_wal_size` 能消除“提前触发”的检查点，调大 `min_wal_size` 能减少新建段。但按时间触发的检查点期间仍会有少量慢写，无法完全消除。以上调优方向**尚未做对照实测**。

## 建议

1. **让检查点只按时间触发**：`max_wal_size` ≥ 1.9 × 高峰期 5 分钟内的 WAL 量，再留 2 到 3 倍余量。按上面的负载，约 4 GB 足够。实际写入更多或数据更大时按比例放大。
2. **保留可复用段**：`min_wal_size` 取平时一个检查点周期的 WAL 量，例如 1 GB。
3. **上线后观察**：PostgreSQL 17 及以上看 `pg_stat_checkpointer` 的 `num_requested` 与 `num_timed`；更早版本看 `pg_stat_bgwriter` 的 `checkpoints_req` 与 `checkpoints_timed`。按 WAL 触发的次数经常出现时，就该调大 `max_wal_size`。日志里出现 “checkpoints are occurring too frequently” 也是同一信号。
4. **估算 WAL 速度**：间隔一段时间两次读取 `pg_current_wal_lsn()`，用 `pg_wal_lsn_diff` 相减再除以秒数；或者看 `pg_stat_wal.wal_bytes` 的增量。

调大的代价：

- 崩溃后需要重放的 WAL 更多，单机重启恢复更慢。有主备自动切换时，这一点影响小。
- `pg_wal` 目录最多会占用约 `max_wal_size` 的磁盘，另加复制槽等保留的部分。

这两个参数都只需重新加载配置即可生效，不用重启。

## 云 PostgreSQL 服务

- **默认值因厂商和版本而异**，常见比社区默认的 1 GB 大，有的按实例规格自动设置。以控制台或参数组里的实际值为准，例如 AWS RDS for PostgreSQL 的默认值通常是 2 GB，但需在自己的实例上确认。
- 一般可以在参数组或控制台里修改 `max_wal_size`、`min_wal_size`，重载后生效。`wal_init_zero` 不一定开放修改，不开放也无妨。
- **存储计算分离的服务**（如 Aurora PostgreSQL）的 WAL 与检查点机制与自建不同，这些参数的意义有限。应按厂商文档和实测判断。
- **云硬盘更敏感**：网络块存储单次刷盘延迟通常高于本地 NVMe。有的还有 IOPS/吞吐上限或突发额度，用完会被限速。同样的检查点或新建段，在云上造成的慢写可能更大、更频繁。选型时优先保证存储档位，比如预配 IOPS、足够的吞吐上限，再调这些参数。
- 在云上上线前，建议用本仓库的定速工具（`deploy/remote-test` 或 `tools/run_receipt_probe.ps1`）按真实写入率跑一轮，确认检查点是否按时间触发、慢写占比是否可接受。

## 与 DBProxy 的关系

- DBProxy 不设置、也不依赖这些参数，它们属于 PostgreSQL 部署配置。
- 本仓库的本地 Compose 和测试环境使用社区默认值（1 GB / 80 MB），所以测试中能看到上述慢写。这是有意保留的，便于暴露问题，不代表推荐值。
- 偶发的几十毫秒慢写不产生错误，也不影响数据正确性。它只在最慢的 0.01% 左右的写入上体现。
