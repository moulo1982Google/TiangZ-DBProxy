# 持续负载下的网络与存储故障：F06、F10（2026-09-24）

都在服务器容器里跑，沿用[持续负载单项注入](acceptance-fault-under-load-20260922.md)的框架：每秒 200 请求，读写各半，32 在途，std 定时，读池 4 写 + 2 读。每轮先正常跑 30 秒，然后注入故障，释放后再正常跑到结束。判定规则在开跑前写进 `fault-plan.json`，由 `tools/analyze_fault_load.mjs` 按阶段判定（规则第 2 版）：

- **故障前**：零错误、零错数据、零漏发。
- **故障中**：零错数据；允许漏发（32 个在途名额占满时直接记为未发出）；只允许事先声明的错误类型。
- **释放后**：释放加 5 秒宽限以后发出的请求，零错误、零漏发。
- **核对**：每次写入要么不在库里（已回滚），要么正好是版本 1、内容正确；返回成功的写入必须在库里。

入口：`deploy/remote-test/run_fault_load.sh --fault <类型>`，多轮串行用 `run_fault_series.sh`。

## F06：保持连接，阻断或延迟 PG 流量

做法：宿主不直接连 PG，而是经过注入器里的一个 TCP 转发层（`acceptance_fault_injector.rs` 的 `pg_pause` / `pg_delay`）。

- `pg_pause`：转发层停止转发，连接保持打开。对 DBProxy 来说，就像网络黑洞：发出去的 SQL 没有回音，连接也不断。
- `pg_delay`：每个方向都加固定延迟。
- 故障结束后恢复正常转发，并记录转发层积压的字节数、各阶段新建了多少连接（用来看有没有重连风暴）。

结果：**四轮全部通过**（`_b` 轮次）。

| 轮次 | 故障 | 故障中：成功 / 错误 / 漏发 / 最慢 | 释放后 | 核对 | 转发层新建连接 |
|---|---|---|---|---|---|
| `f06_pass_b` | 经过转发层，但不加故障（对照） | 3,002 / 0 / 0 / 8.5 ms | 零错误 | 7,000 零差异 | 0 |
| `f06_pause5_b` | 停转 5 秒 | 1,031 / 15 / 955 / 5.0 s | 1.9 ms 后恢复，零错误 | 6,517 零差异，13 次报错均已回滚 | 0 |
| `f06_pause30_b` | 停转 30 秒 | 1,000 / 78 / 5,923 / 20.0 s | 0.18 s 后恢复，零错误 | 10,031 零差异，41 次回滚，4 次“结果未知”实际已写入 | 0 |
| `f06_delay20_b` | 每方向加 20 ms，10 秒 | 1,237 / 16 / 1,748 / 2.4 s | 1.1 ms 后恢复，零错误 | 6,125 零差异，16 次报错均已回滚 | 0 |

怎么理解：

- **已经发出的 SQL 没有执行时限**（按设计，见 `postgres_request.rs` 的说明）。停转期间，这条 SQL 会一直等到网络恢复，并占住它所在分片的连接。
- **排队等这条连接的请求，2 秒后明确失败**：返回 `StorageUnavailable`，这时一条 SQL 都没发出，全部已回滚。所以错误是有上限、说得清的，队伍不会无限变长。
- **客户端时限**：压测客户端每次请求等 10 秒，SDK 会自动重发一次，所以最长 20 秒后返回“请求超时，结果未知”（30 秒那轮有 32 次，正好是在途上限）。其中 4 次的 SQL 在网络恢复后真的提交了。这是如实的“结果未知”，不是假失败：客户端用同一个请求号重试，会拿到“重复”和原版本。**没有一次把没写进去的请求报告成成功。**
- **没有重连风暴**：连接一直开着，转发层在故障中和故障后新建的连接都是 0。恢复后积压的约 8–9 KB 在 10–22 ms 内转发完。
- **延迟 20 ms**：每来回一次多 40 ms，一次写事务要来回好几次，单个分片的吞吐大幅下降。等不到连接的请求在 2 秒后失败，释放后立刻恢复。
- **转发层自身的开销**：对照轮正常阶段 P50 3.9 ms、P99 6.9 ms；直连的 `f10_ro_a` 是 P50 3.6 ms、P99 4.9 ms。所以本组的延迟数字比直连约高 2 ms，但判定结论不受影响。

保留的第一组 `_a`：判定同样全部通过，但当时转发层对“无延迟”的数据也调用了一次定时等待，每个数据包多等约 1 ms，正常阶段写入 P50 被拉到 10 ms、P99 到 61 ms，延迟数字不可用。修正后重跑得到 `_b`。

边界与建议：

- 转发层自己会回 TCP 确认，所以这里模拟的是“SQL 响应不回来”，而不是网络真丢包。真丢包时，操作系统会重传；不加保护时要等系统放弃原连接，时间取决于内核和配置，不能统一承诺“Linux 约 15 分钟”。这期间其他请求可能在连接排队预算耗尽后失败。
- 建议给 PG 连接配置 TCP 保活或发送超时，让 DBProxy 能在可控时间内发现“对端已死”并重连。本轮没有改代码。
- 停转期间，读池连接同样可能卡住。本组的读取绝大多数成功，但没有单独统计读池卡住的情况。

## F06 补充：真实断网与连接保护（2026-09-24 至 09-28）

转发层模拟的“对端不回应”，其实操作系统还是会回确认，所以测不出“网络真断、对端消失”时的问题。这一组改用真实断网来测：

- 起一个一次性 PG，数据放在内存盘上。压测进行中，用 `docker network disconnect` 把它从测试网络上摘下 90 秒。这期间发往它的数据包直接消失，没有拒绝，也没有确认。之后再接回网络。
- 主机脚本是 `deploy/remote-test/run_f06_netcut.sh`，注入器用 `external` 类型，通过文件和主机脚本对时间。

### 修复内容（连接保护）

DBProxy 连 PG 时，如果连接串里没有写，就默认加上两项保护：

- Linux TCP 连接的未确认数据配置 30 秒发送超时；它不是 SQL 执行超时；
- 空闲 30 秒开始保活探测，间隔 10 秒、次数 3；实际断开时间受平台及发送超时等选项共同影响。

连接串参数优先于默认值，时长单位为秒，`keepalives_retries` 是次数。2026-09-29 又修复显式零值/库默认值被覆盖的问题，三条单元测试覆盖 URL、关键字、编码参数和密码边界。平台范围及完整复测见 [断网收尾](acceptance-f06-netcut-20260929.md)。

对比方法：用同一个版本，通过连接串参数 `keepalives=0&tcp_user_timeout=3600` 把保护关掉，模拟修复前的行为；另一轮用默认值。

### 第一组 `_a`（重新接回后地址没变）

| | 关掉保护 `f06_cut_off_a` | 默认保护 `f06_cut_on_a` |
|---|---:|---:|
| 断网期间：成功 / 报错 / 漏发 | 308 / 287 / 21,463 | 3,936 / 11,752 / 6,370 |
| 网络恢复后多久不再出错 | 18.7 秒 | 0.4 秒 |
| 核对 | 10,255 零差异（4 次“结果未知”实际已写入） | 17,803 零差异 |

- **关掉保护**：断网期间请求卡在已发出的 SQL 上，32 个在途名额被占满，几乎发不出新请求。网络回来后，要等操作系统下一次重传才恢复；断了 90 秒后，重传间隔已经退避到十几秒。
- **默认保护**：坏连接被及时断开，请求快速、明确地失败。网络一回来 0.4 秒就恢复。
- 两轮都判为失败，原因相同：故障前的正常阶段有约 10 次漏发。这是计时问题：脚本在断网命令执行完之后才记下时间，而网络在命令执行中途就已经断了，断网前最后几百毫秒的请求被算进了正常阶段。
  - 已改成断网前先记时间，注入器以主机的时间为准。
  - 同时发现，重新接回网络后 PG 拿到的还是原地址，所以没有测到“换机器”的情况。
  - 这两轮保留，修正后重跑为 `_b`。

### 第二组 `_b`（断网后用占位容器占住原地址，PG 回来时换新地址）：作废，保留

- 计时修正生效了：两轮故障前的正常阶段都是零漏发、零错误。PG 回来时也确实换了地址（`.5` 变成 `.7`）。
- 但关掉保护和默认保护的结果几乎一样：

| | 关掉保护 `f06_cut_off_b` | 默认保护 `f06_cut_on_b` |
|---|---:|---:|
| 断网期间：成功 / 报错 / 漏发 | 3,972 / 18,046 / 133 | 3,952 / 18,044 / 135 |
| 网络恢复后多久不再出错 | 0.37 秒 | 0.39 秒 |

- 原因：占位容器拿到原地址后，DBProxy 发往原地址的数据包由占位容器的系统接收，而它没有这些连接，所以直接回“拒绝”（RST），旧连接马上断开。这等于把“对端消失”变成了“对端明确拒绝”，这一组不能用来比较保护的效果。判定都通过，只能说明断开后的重连是好的。
- 占位容器用的是 PG 镜像，每次启动会自动带出一个匿名数据卷。清理时发现本次测试一共留下 7 个空的匿名卷（F10 和断网测试各轮留下的），已确认是自己留下、没有被任何容器使用后删除。脚本已改为删容器时一并删除它的卷。

### 第三组 `_c`（每轮单独建一个小网络，PG 用固定地址，回来时换另一个固定地址，原地址没人接）

两轮均已结束并退出 1，不能算整轮通过。2026-09-29 排查确认：默认保护轮业务阶段与 17,782 次写入核对通过，但独立采样连接卡在旧地址，挡住宿主正常退出；关闭保护轮连业务核对也未完成。修复与新编号复测见 [F06 断网收尾](acceptance-f06-netcut-20260929.md)。保留原始失败，不覆盖。

## F10：数据库只读

做法（`f10_ro_a`，没有经过转发层）：

1. 把本轮测试库设成“新会话默认只读”，然后切断 DBProxy 的现有连接（8 条），让它重连进只读状态，保持 10 秒。
2. 释放时恢复可写，再切断一次（6 条），让它重连回可写状态。

结果：**通过。**

| 阶段 | 响应 | 成功 | 错误 | 错数据 | 漏发 | 最慢 |
|---|---:|---:|---:|---:|---:|---:|
| 故障前 | 6,003 | 6,003 | 0 | 0 | 0 | 11.5 ms |
| 故障中 | 3,001 | 2,000 | 1,001 | 0 | 0 | 79.0 ms |
| 释放后 | 4,996 | 4,996 | 0 | 0 | 0 | 19.2 ms |

- 只读期间：写入全部返回 `StorageUnavailable`（“用同一个幂等键重试”），读取全部正常。没有请求卡住，也没有漏发。
- 核对：7,000 次写入零差异。1,001 次报错的写入全部不在库里，没有“报错但其实写进去了”的情况。
- 释放后立刻恢复，最后一个受影响的请求就在释放那一刻。
- 客户端只看到“存储不可用”，看不出是“数据库只读”。日志里的原因也只有 `db error`，与 [F15 的发现](acceptance-fault-process-20260924.md) 相同。这个问题当天已修复：日志现在会写出 SQLSTATE 和消息，只读时是 `25006`。本轮的只读故障没有在修复后重跑。

## F10：磁盘满

做法（`f10_disk_a`，主机脚本 `deploy/remote-test/run_f10_disk_full.sh`）：

1. 另起一个一次性 PG 18.6 容器，整个数据目录放在 1 GiB 的内存盘卷上（tmpfs），WAL 上限调到 256 MB，保证 PG 本身放得下。
2. 工作台也挂载同一个卷。注入器用一个占位文件把剩余空间全部写满（本次写了 943 MiB，写到 `No space left on device` 为止），保持 15 秒，然后删除占位文件。
3. 脚本会先检查占位目录必须是 tmpfs，否则拒绝运行，所以真实磁盘不可能被写满。跑完以后，一次性 PG 容器和内存盘卷都删除，PG 日志保留。
4. 这一轮事先声明允许的错误，额外加上 PG 在磁盘满和崩溃重启时的报错文字；恢复宽限改为 15 秒。

结果：**通过。**

| 阶段 | 响应 | 成功 | 错误 | 错数据 | 漏发 | 最慢 |
|---|---:|---:|---:|---:|---:|---:|
| 故障前 | 6,104 | 6,104 | 0 | 0 | 0 | 12.7 ms |
| 故障中（15 秒 + 宽限） | 6,020 | 4,549 | 1,471 | 0 | 0 | 17.9 ms |
| 释放后 | 1,876 | 1,876 | 0 | 0 | 0 | 5.9 ms |

- 磁盘满期间，写入都在十几毫秒内明确失败，返回 `StorageUnavailable`。PG 日志里对应 1,472 条 `could not extend file …: No space left on device`，其中 1 条是 PG 自己的统计表。读取全部正常，没有漏发。
- 核对：7,000 次写入零差异。1,471 次报错的写入全部不在库里，没有写一半的事务，也没有“报错但写进去了”。
- 删除占位文件后立刻恢复，释放那一刻以后的请求全部成功。PG 没有崩溃重启（重启次数 0）。

边界：

- 这一轮只碰到“数据文件扩展失败”（普通错误）。WAL 用的是事先分配好的段，所以没有走到“WAL 写不下、PG 崩溃重启”的路径。那条路径需要 WAL 在故障中也要新建段，可以加大写入量或延长时间再测。
- 计划里的“日志写入失败”没有测。

## 小结

| 项目 | 结论 |
|---|---|
| F06 阻断 / 延迟 | 通过（转发层模拟；真丢包时卡住 SQL 的时长取决于系统 TCP 设置，建议配置保活或发送超时） |
| F10 只读 | 通过 |
| F10 磁盘满 | 通过（数据文件扩展失败路径；WAL 写满导致崩溃重启的路径未覆盖；日志写入失败未测） |
