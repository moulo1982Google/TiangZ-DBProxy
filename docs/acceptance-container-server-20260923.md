# 容器内运行与服务器对照（2026-09-23）

在一台共享 Linux 主机上，把 PG、Redis、DBProxy 宿主、发压和注入器全部放进容器运行，与笔记本（Windows + Docker Desktop）的同参数结果对照。主机上只依赖 Docker，不安装工具链、不留源码。方法与脚本见 [`deploy/remote-test/README.md`](../deploy/remote-test/README.md)。**这不是两小时验收，也没有定位旧尖峰。**

## 环境

| 项 | 笔记本 | 服务器容器 |
|---|---|---|
| CPU | Ryzen 9 7950X，16 核 32 线程 | 2× Xeon E5-2680 v4，28 核 56 线程 |
| 内存 | 31 GB | 94 GB |
| 系统 | Windows 10 + Docker Desktop (WSL2) | Ubuntu 22.04 + Docker 29 |
| 数据盘 | 单块 Intel P3600 1.2 TB | 两块同型号 P3600 RAID0（`/data`） |
| 测试进程 | Windows 主机进程 | 工作台容器，cpuset 20-27,48-55，16 GB |
| PG/Redis | 容器，4 CPU / 8 GiB / shared_buffers 2 GiB / max_connections 30 | 同上，另钉 cpuset 14-17,42-45（NUMA 节点 1） |
| 其他负载 | 桌面应用、集显驱动 | llama serve、ComfyUI、gitea（未钉核） |

服务器是共享机器，测试期间其他服务照常运行，因此这里的数字不是该硬件的容量上限。

## 一分钟定速短测

参数相同：每秒 200 请求、1 KiB、读写各半、32 在途、std 定时、读池 4 写 + 2 读、SDK split4、清理开启、10 秒预热 60 秒测量。

| 指标 | 笔记本 `probe_20260922ag` | 服务器 `probe_srv_c` |
|---|---:|---:|
| 漏发 / 错误 / 数据不符 | 0 / 0 / 0 | 0 / 0 / 0 |
| 核对写入 | 7,000 | 7,000 |
| 合计 P50 / P99 | 4.749 / 6.570 ms | 3.651 / 4.945 ms |
| 读取 P50 / P99 / 最大 | 未单独计算 | 3.497 / 3.692 / 7.533 ms |
| 写入 P50 / P99 / 最大 | 未单独计算 | 4.520 / 5.065 / 43.256 ms |
| 发送迟到 P99 | 0.743 ms | 0.248 ms |
| 诊断事件 / 丢失 | 21,001 / 0 | 21,001 / 0 |
| 诊断单条写入最大 / 累计 | 0.106 / 6.5 ms | 0.492 / 51.5 ms |
| PG 慢 SQL（≥20 ms） | 0 | 5 条 COMMIT，28–38 ms（见下方更正） |

服务器端更稳：发送迟到 P99 降到三分之一，合计 P99 低约 1.6 ms，读取 P99 只有 3.7 ms。诊断写入开销在服务器上更高（累计 51.5 ms），因为证据写到 RAID0 绑定目录且队列深度到 2，但仍远小于测量窗口，可以忽略。

服务器端分段计时：读池在用峰值 1（容量 2），取连接等待 14,000 次全部在 1 ms 桶内；读取处理最大 9.428 ms，同记录顺序等待最大 0.003 ms；写入处理最大 42.722 ms，PG 写操作有 4 个样本落在 25–50 ms 桶。运行时心跳最大延迟 2.081 ms，而笔记本上是 25 ms 量级——这是两台机器最明显的差别，也说明笔记本的整机停顿确实存在。

**单次 43 ms 的慢写仍然出现**。它发生在没有集显、没有 Windows 调度问题的环境里，说明这一类写入尖峰不能全部归因于笔记本的机器停顿。旧的 100 ms 级尖峰没有复现。

> **更正（2026-09-23）**：本报告初版写“PG 没有记录慢 SQL”，这是错的。服务器上 PG 日志文件默认权限 0600，工作台容器以普通用户运行，截取时读失败却没报错，得到的是空文件。修正权限后从完整日志补回各轮时间窗（原空文件改名为 `postgres.log.empty-at-capture` 保留，补回说明在 `postgres.log.recovered.txt`）。按每轮自己的负载窗口统计：`probe_srv_c` 有 5 条 COMMIT 耗时 28–38 ms，恰好落在 01:52:45.978 和 01:53:26.528 两次慢写时刻；`fault_blocked_srv_a`、`fault_kill_srv_a` 也各有 4 条同类 COMMIT；三轮期间都没有检查点。原因定位见[写入尖峰定位](acceptance-spike-localization-20260923.md)：新建 WAL 段时提交排队。脚本现已在日志不可读时直接失败。

## 持续负载中的单项故障注入

规则与第 2 版阶段判定相同，跑前写入 `fault-plan.json`。

### 卡住一条写 5 秒（`fault_blocked_srv_a`）

| 阶段 | 响应 | 错误 | 漏发 | 最慢端到端 |
|---|---:|---:|---:|---:|
| 正常 | 6,002 | 0 | 0 | 40.2 ms |
| 故障 | 1,683 | 31（全部允许类型） | 319 | 4,017.6 ms（被卡的那条写） |
| 恢复 | 5,996 | 0 | 0 | 42.9 ms |

注入后 1.003 秒观察到目标写在等锁，释放后 4.6 ms 等待者清空，最后一次扰动距释放 1.5 ms。31 个错误全部回滚，6,841 次写入核对零差异。与笔记本（31 错误 / 354 漏发）几乎一致，说明这个行为由 DBProxy 的连接预算决定，与机器无关。

### 杀掉全部 DBProxy 连接（`fault_kill_srv_a`）

| 阶段 | 响应 | 错误 | 漏发 | 最慢端到端 |
|---|---:|---:|---:|---:|
| 正常 | 6,002 | 0 | 0 | 43.3 ms |
| 故障 | 1,001 | 1（在途写，已回滚） | 0 | 68.8 ms |
| 恢复 | 6,997 | 0 | 0 | 43.5 ms |

终止 8 条连接（4 写 + 2 读 + 2 维护），自动重连，7,000 次写入核对零差异。与笔记本两轮结果一致。

## 容器方案的组成与已修问题

- `deploy/remote-test/Dockerfile.workbench`：`rust:1.91-bookworm` 加 psql、node、procps，复制整个工作区并预编译 release 二进制与真实库测试二进制。
- `deploy/remote-test/deps.sh`：主机没有 Docker Compose 插件，改用等价的 `docker run` 起三个依赖容器；`docker-compose.yml` 同时保留给有插件的环境。
- `deploy/remote-test/{common,run_receipt_probe,run_fault_load}.sh`：PowerShell 编排脚本的容器内 bash 版本，证据结构一致。PG 日志按共享日志文件的字节偏移截取窗口。
- 运行工作台容器必须带 `--user $(id -u):$(id -g)`，否则证据文件归 root，宿主用户无法清理。
- 已修两处脚本缺陷：`wait` 等不到非子进程（改为用 `host.exit` 记录退出码）；`HOST_PID=$(start_host ...)` 因后台子 shell 持有命令替换管道而死锁（子 shell 加重定向）。两次失败痕迹已清理，未计入结果。

## 边界

- 共享主机：CPU 用 cpuset 隔离，内存带宽和磁盘仍与 llama、ComfyUI 共享。
- 一分钟负载，一次只注入一项故障，故障来自事务锁或终止连接，不模拟磁盘或网络变慢。
- 宿主进程全程存活，不是独立 DP 进程崩溃恢复。
- 未做两小时验收；旧尖峰未定位，但服务器上出现的 43 ms 慢写是新线索。
