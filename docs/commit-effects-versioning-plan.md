# Commit effects 编码兼容方案（D1，尚未实施）

当前 `dbproxy_multi_transaction_effects.payload` 保存规范化 CommitEffects 的 bincode standard 字节，重试以完整字节相等验证。同一 operation_id 的历史行已经存在，不能直接给新编码添加字节头，也不能在升级时重写历史 payload。wire fingerprint 与该持久编码属于两份不同契约。

## 建议分两阶段实施

第一阶段冻结旧契约，保持写入字节不变：独立定义持久 DTO V0（包括 RecordKey、AppendRecord、OutboxEvent 的字段顺序及类型），冻结规范化排序、验证和 bincode 配置，禁止直接依赖未来会扩展的通用领域结构。以基线实际编码生成固定字节样本，覆盖非空 append、非空 outbox、二者组合、多记录排序和边界整数；测试必须从固定历史字节读取，不能让测试与实现同时重新编码而一起漂移。

随后新增带非负约束的 `encoding_version SMALLINT NOT NULL DEFAULT 0` 列。通过新增列默认值标识历史行，保持旧 payload 不动；当前效果表触发器拒绝所有 UPDATE/DELETE，新增版本列也应继续受其保护，不能开放版本更新。第一阶段新服务仍写 V0，让旧服务能读取相同格式，不在列出现时就切换写入编码。

第二阶段引入 V1：新写入显式存版本，重试先读持久行的版本，再用该版本的 DTO/规范化规则比较效果。版本未知时返回明确的“不支持该持久编码”错误，不回退解码，也不误报 OperationIdConflict。新字段映射到 V0 只有在业务契约明确认定为默认且无效果时才可接受；不能丢弃非默认新增效果后误判相同操作。无 effects 行的历史普通事务继续按原有空效果规则处理。

使用独立版本列，避免“无头旧 payload 的首字节恰好等于新版本号”的识别歧义。版本标识只解决识别问题；跨版本效果的等价关系仍需逐项定义。

## 发布与回退约束

先发布能读 V0/V1、仍写 V0 的服务，再确认所有效果写入/重试处理实例已升级，最后开启 V1 写入。在开始写 V1 后，不能直接回退到只支持 V0 的 binary；应回退到仍能读取 V1 的兼容版本。不得用更新旧 effects 行或替换 operation_id 的方式实现回退。

这一方案独立于迁移 010 的队列切换要求；所有相关实例的迁移、队列和编码要求都必须满足。不得在固定版本长测期间切换编码。

## 验收门槛

- 旧 V0 数据库行在新服务中以原 operation_id 重试，返回原回执；快照、追加记录和 outbox 不增加。
- 相同 ID 的 payload、排序后效果或非默认新增效果发生改变时，仍返回冲突。
- V0/V1 并存、无 effects 行、未知版本、损坏字节都有明确结果。
- 行 payload/版本不可变，重复请求和并发请求仍保持原子性。
- 切换前旧读者与新 V0 写者互通；切换后旧读者不得混入验收对象，回退兼容版本能够重放已写入 V1。

本文件仅记录方案。本轮没有修改效果编码、协议、历史数据或引入该版本列。
