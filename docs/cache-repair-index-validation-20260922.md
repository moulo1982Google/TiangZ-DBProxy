# 缓存修复领取索引验证（2026-09-22）

后续复测发现变化重试日期的分布可能读取更多索引页；固定日期和变化日期测试现已分开，详见[复测修正](outbox-hybrid-validation-20260922.md#同轮发现的缓存修复测试问题)。下列页数是当时样本，不代表固定成本保证。

本轮处理缓存修复队列积压，新增迁移 014。Docker 使用已授权的 PostgreSQL 18.6-bookworm、Redis 8.8.1-trixie；测试库与业务库隔离。没有开展容量承诺、长时间压力或故障矩阵测试。

## 修改内容

- 分别定位尚未领取、租约已过期的第一条任务，再按原来的 requested_at、namespace、record_key 顺序选择一条。
- 保留到期索引，增加未领取排序、租约到期、已领取排序三个索引。日期列作为索引键，允许在读取业务行前过滤。
- 每条 SQL 最多短暂锁住两条候选，只更新一条。正常领取接口使用单语句自动提交，另一条锁随语句结束释放；并发工作者仍跳过已锁定任务，不承诺严格的并发完成顺序。
- available_at 和 lease_until 都按本条语句开始时间判断；执行中才到期的任务留给下一轮。新租约起点仍取更新时的实时钟，确认/失败处理的租约校验不变。
- 启动检查增加这三个索引的结构检查，覆盖缺失索引和错误筛选条件；共检查 18 张表的主键、16 项辅助索引以及 32 个快照分区主键。

## 十万条积压对比

每种分布 100,001 行，使用同一事务中的保存点对比：旧查询加旧索引布局，与新生产 SQL 加迁移 014 布局。查询后回滚，核对真正领取的记录，再清理测试事务。没有关闭顺序扫描，也没有强制索引。页数是共享缓存命中与读取次数之和，并非磁盘物理读取量或不同页面数。

| 分布 | 旧/新读取页数 | 旧/新耗时（毫秒） |
| --- | ---: | ---: |
| 全部可领取 | 1257 / 27 | 19.290 / 0.152 |
| 大量延后重试 | 11 / 20 | 0.071 / 0.101 |
| 大量有效租约 | 1341 / 24 | 7.658 / 0.106 |
| 大量过期租约 | 1350 / 29 | 21.984 / 0.214 |
| 延后重试与有效租约混合 | 1290 / 381 | 7.577 / 1.416 |
| 大量死信 | 10 / 18 | 0.085 / 0.116 |
| 没有可领取任务 | 1333 / 3 | 8.009 / 0.065 |

混合分布仍需要读一部分索引，不能保证数据量增长时永远只读固定页数。原来已经很快的延后重试、死信场景略有增加。毫秒数只是本机单次样本，受缓存和执行顺序影响，不是吞吐量承诺。

同样更新 1,000 条租约：旧/新耗时 8.324 / 11.265 毫秒；共享页面访问 14989 / 19765；数据库日志 WAL 361802 / 592253 字节，约增加 64%。新增索引还占磁盘空间。保留这些成本数据，避免只展示读取收益。
