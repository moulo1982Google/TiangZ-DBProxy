# 同库快照批次只提交一次

2026-09-07。前一项缓存清理修复 `24d66b7` 已让原 100 玩家启动通过，但长跑在 18 分钟后的健康阶段仍出现 Actor RPC 超时。失败前约 37 秒内，主 DBProxy 的 `save_multi_snapshot` 完成 98 次，平均约 1,144 ms；PG 排队均值约 665 ms、操作均值约 279 ms，提交后缓存同步均值已约 2 ms。该数据说明仍有写入等待，不能把全部问题归到已经移出的缓存 ACK。

旧 `StorageBackend.save_multi` 根据每个 RecordKey 把同一批写入拆到所有连接分片，每组单独事务提交，再等待所有组返回。这些连接指向同一个 PG 数据库，不是独立物理数据库；拆分会放大提交次数及每个 RPC 同时占用的连接数。真实回归使用两条连接、32 条独立记录，旧实现观察到两次 PG 操作，单批一次的断言失败；修改后一次操作且结果正确。

现在按批次首记录稳定选择一条连接，复用原 `TieredSnapshotStore.save_batch` / `PostgresSnapshotStore.save_batch` 一次提交。批内按 namespace/key 排序处理以保持重叠批次取锁顺序，响应重新排列为调用者的原顺序。空批直接返回；服务端原记录数、payload 和去重验证不变。Backlog 批量落库复用该路径，读批次与单条写入的路由不变。

这不是新的跨记录业务事务承诺：每条 CAS/幂等冲突仍返回独立失败，其他有效记录仍可提交；需要全有或全无仍使用 CommitRecords。网络/SQL/COMMIT 回包失败仍按原 ID 恢复，不能从整体错误推断未提交。请求预算、连接数、PG 持久化、Redis AOF 和业务超时没有改变。

真实回归另覆盖原批重复提交、混合 CAS/幂等冲突、失败条目不推进版本、成功条目重试返回 Duplicate，以及反向输入的重叠批次只产生一个 CAS 胜者。完整 30 分钟结果待新候选重新验收。

候选 `4432808` 的第二轮 `20260907-cleanup-batch-30m-r2` 在前置故障套件失败，未启动计时。可靠 Redis AOF 重放约 8.8 秒后 ready，但测试原先只轮询约 10 秒，短于 Compose 的 5 秒间隔、12 次健康检查窗口；首项失败留下队列项后，后续 Superseded 测试也失败。保留 `redis-startup.log`、健康配置及失败日志。测试就绪等待调整为 70 秒，覆盖既有 Compose 健康窗口；应用 RPC/PG 预算、负载、持久化和数据断言均不变。需要独立新轮次重新验证，不能覆盖失败记录。
