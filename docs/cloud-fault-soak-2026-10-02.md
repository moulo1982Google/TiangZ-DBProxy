## 逐阶段门禁

完整独立阶段依次为 **30 / 60 / 120 / 240 / 480 / 960 / 1440 分钟**。每阶段新 PG 数据库及 Redis 逻辑库，保留前阶段数据，不 FLUSH、清表或拼接部分时长。每阶段结束还要完成维护排空、额外 300 秒空载观察、真实进程退出和原始证据独立复核；这些额外时间不算负载资格。失败停止递进并保留现场，全部完成后停止本轮资源，连续完整 86400 秒才有该阶段的 24 小时资格。

每阶段都包含五类故障，30 分钟阶段在第 120 / 420 / 720 / 1020 / 1320 秒开始：

1. 首选 DBProxy SIGKILL，等待 15 秒后启动同一冻结制品；副节点整阶段不重启。
2. 缓存 Redis SIGKILL，15 秒后重启；无持久化，因此真实丢失缓存。
3. PG SIGKILL，20 秒后重启，实际 SQL 恢复就绪。
4. 仅将三个专用存储容器与其私有 bridge 断开 15 秒并重新接入；不操作宿主网卡或已有业务网络。
5. 停 PG 并确认仍有 AOF 入队进展，冻结两台 DBProxy，读取全部 100 玩家条目及 pending / processing / lease / sequence 语义状态，强杀并重启可靠 Redis。写进程恢复前两次规范化 SHA 必须完全一致，再恢复 DBProxy 与 PG；不能用后续覆盖掩盖丢数据。这不是整机断电验收。

可重试可用性错误仅允许在五秒客户端观察区间与声明故障/恢复窗口相交时发生；数据不变量在故障期间也必须零错误。存储累计超时增量的**完整观察区间**须包含在一个故障窗口内，不能推定增量在某一个时刻发生。恢复原限 180 秒，要求客户端和两节点存储计数同时连续健康至少 60 秒，事务、交易、入队都继续进展；最终至少 180 秒无故障尾段。

独立复核重新读取原客户端日志、实际退出状态、逐代累计指标及 AOF 见证；SQL 核对直接写序号/回执、每笔交易的两条守恒分录、事实/回执/快照/Outbox 数量，以及 Stream 的完整事件 ID 集合。另以有界 SQL 分页和磁盘索引逐条比较所有事件原始 payload / metadata，并单独报告至少一次重复投递，避免把 24 小时全量 JSON 装入 512MiB 控制进程。

运行时每 5 秒保留父/子 cgroup、CPU、anon/file/shmem/swap/OOM、实际 PID 代次的 RSS/PSS/私有页；每 30 秒只读采样未发布 Outbox 和有界 PG 活动。正常窗口 SQL 积压峰值 100、正斜率上限 0.05 条/s、前后均值增长上限 32，空载期间须持续为零；最终排空不能掩盖持续积压。采样时退出的 PG 进程标为未知，不补零或累加 PG RSS 充当独占内存；Rust 长阶段 RSS/PSS 基线单独检查。

## 首轮失败与重新启动

最初 `tzfault20261002` 在负载就绪后的第一次 SQL 观察失败，协调器为 `JSONDecodeError`。`json_agg(a)` 可返回跨多行数组；按 `stdout.splitlines()` 拿第一行不构成完整 JSON。另有停机记录问题：成功结束的 systemd service 可能丢失旧退出元数据；清理代码随后向已退出 PID 强杀时抛错，阻断最终 runner report。协调器失败状态、原 stderr / journal / 启动日志均保存，不能根据残留 runner `running` 报告判断测试继续或通过。

三个专用容器与全部节点已独立核实停止；61 个原始文件冻结归档，SHA-256 `b172e063038de482964f89693af9036dee0d8f06908b6e8401786fe973237962`，数据卷保留，负载资格为零。修复控制器使用完整 JSON framing、紧凑 JSONB 与原 stdout 留档；服务保留退出代次并校验 ExecMainPID / Code / Status，清理报告不因已退出 PID 再次中断。产品 ELF / SDK / 超时默认值均未改。

重新准备时又复现已有的 Docker Mounts 顺序误报，只是列表顺序变化，完整挂载记录、网络、PID、配置未变；按完整记录规范化排序修复，未删保护。此前失败保护检查后错误地执行了依赖准备步骤，产生不含保护快照的本地包，该包未上传；补齐前置验证后重新冻结。附加观察器的嵌套脚本定界符错误只发生在本机解析阶段，尚未启动 SSH；修复后先解析再安装，故障计划与运行中的产品输入未改。
