# F07 锁冲突与 A06 回执时间补测

本轮沿用 220 的测试 PG/Redis 容器，不停止数据库，不操作旧库。每个测试使用新数据库；工作台限制为 4 CPU、16 GiB，并固定到既有测试 CPU 集合。只在 F06 三轮定速测量结束后编译和执行。

## F07：真实进程的锁与退避

入口：`crates/dbproxy-server/tests/fault_process.rs` 的 `f07_cleanup_skips_rows_and_backs_off_on_table_lock`，经 `run_fault_process.sh` 的 `FAULT_TESTS` 选择。服务为重新构建的 release 正式进程，清理节奏使用正式默认值，不缩短一分钟空闲/失败等待。

夹具与断言：

- 1,101 条过期回执、100 条近期回执、一份通过真实 SDK 写入的业务快照。
- 启动前锁住其中 101 条过期回执；后台清理应先删除未锁的 1,000 条，删除指标对应，失败数为 0。放锁后剩余 101 条清掉。
- 对普通回执表持 EXCLUSIVE 锁，观察真实清理失败计数增加一次、日志 SQLSTATE `55P03` 与 60 秒重试说明。之后十秒中错误计数不再增长，业务权威读取仍正常。
- 在持锁连接中插入 501 条过期回执后提交放锁。等待正式退避结束，核对继续删除、近期 100 条保留、业务原请求仍返回 Duplicate。删除总数应为 1,602。
- 记录行锁跳过耗时、释放表锁后的恢复耗时、失败到恢复的间隔和各阶段监控；不把等待一分钟当作重连异常，也不改阈值来加快测试。

本项不覆盖 A14 正常停止各阶段，也不以表行数替代 A15 全内容账本。

## A06：业务时间与保留期边界

入口：`crates/dbproxy-storage/tests/receipt_retention.rs`：

- `business_time_never_controls_receipt_age_or_renews_it`：业务时间 0、1 毫秒和 2100 年；每种时间验证新回执不会因业务时间过旧而删除，重复请求不改变 recorded_at；23 小时保留、25 小时删除，快照内容/版本/业务时间不变。
- `cutoff_is_strict_and_expired_receipts_do_not_bypass_cas`：24 小时和 1 小时分别检查截止前一秒、恰好截止、超过一秒。插入和生产清理 SQL 在同一个 simple-query 消息中使用同一 statement_timestamp，只有严格过期的那条删除；过期后原 CAS 仍不能重复应用。

不改主机/PG 时钟，只修改新测试库中的 recorded_at。库级证据不声称为完整真实进程事务矩阵。明确跳过 `migration_grants_old_receipts_full_retention`。

## 结果与复测

F07 真实进程通过，RunId `f07_20260929a`，数据库 `f07_20260929a_f07`：

- 行锁期间约 1.025 秒删除未锁的 1,000 条；放锁后再删 101 条。
- 表锁失败一次，十秒观察期间没有频繁重试；之后从失败到恢复完成约 61.052 秒，释放表锁到清完约 50.896 秒，符合一分钟退避再分两批删除的节奏。
- 总删除 1,602，近期 100 条未删，业务回执重放 Duplicate；真实监控计数和 SQLSTATE 断言通过。
- 测试总耗时 124.30 秒。原始证据位于服务器 `/data/dbproxy-test/evidence/fault_process_f07_20260929a/` 和本地 `target/server_20260929/fault_process_f07_20260929a/`。

两项新增入口在 Windows 编译通过，Clippy 无警告。

A06 真实库通过，两个入口分别使用新库 `a06_20260929a_time`、`a06_20260929a_cutoff`：

- 三种业务时间逐项通过新回执保留、两种年龄下重试不续期、过期删除与快照保护。
- 86,400 秒和 3,600 秒保留期的前一秒/恰好/后一秒全部符合严格过期规则，CAS 保护仍生效。
- 两项测试分别耗时 0.45 秒、0.47 秒；是功能正确性验证，不作为性能数字。
- 证据位于服务器 `/data/dbproxy-test/evidence/a06_20260929a/` 和本地 `target/server_20260929/a06_20260929a/`，旧库升级测试未运行。
