## 不改变的业务契约

- 普通 CAS 重试沿用请求 ID、记录、schema、期望版本、payload 和时间字段；不同内容不能借用旧 ID。
- `SaveMultiSnapshot` 是逐条结果，允许部分成功；重试逐条恢复原回执，不能按全成功/全失败处理。
- `ApplyMultiTransaction` / `CommitRecords` 在同一数据库原子提交。COMMIT 回包丢失是结果未知，必须查回执/用原 ID 与原内容恢复，不能生成新操作号或重新抽取业务效果。
- 默认权威读取与显式缓存读取仍分开；数据库故障不能静默切到内存。缓存写超时不抹掉已提交事实，应保留 durable repair。
- queued sequence 仅保护该队列的先后次序；不据此承诺同一键任意混用 queued/direct/事务写安全。
- Outbox 至少一次。MQ 已确认而数据库尚未 ACK 的崩溃窗口允许再次投递；消费组以稳定 event ID 去重，inbox 与投影同事务后才确认 MQ。该测试消费表只是示例，不是新增生产 inbox 服务。

## 本轮选定用例

| 用例 | 真实依据 |
| --- | --- |
| `lost_commit_reply_recovers_the_same_receipt_and_exactly_once_effects` | 代理在真实 PG 返回 COMMIT 成功后丢回包；恢复首次结果，快照/事实/Outbox 各只应用一次 |
| `generic_commit_preserves_atomic_effects_and_immutable_facts` | CAS 失败整体回滚、原操作重放与效果身份、追加事实不可变 |
| `postgres_and_redis_preserve_snapshot_semantics` | 同 ID 同内容重放、变更 payload/时间拒绝、CAS 与缓存 revision |
| `snapshot_batch_uses_one_commit_and_preserves_independent_results` | 批量部分冲突仍返回独立结果，原批次重放，反向输入的重叠写 |
| `acknowledged_write_timeout_must_not_expose_old_cache` | 暂停本轮 Redis 写，已提交 ACK 后独立读取不能返回旧缓存 |
| `queued_flush_fence_keeps_the_newest_sequence` | 延迟 queued 写不能覆盖新 sequence，仍不扩大混合模式保证 |
| `relay_routes_leases_audit_and_two_consumer_groups` | AOF 确认后未 ACK 模拟恢复，真实两条 Stream 消息由两个消费组各只应用一次 |

本轮上述 **7 个真实存储用例全部通过**，逐项串行执行，原断言未修改。五个 storage/postgres_redis 用例的日志为 `temp/v0.7-recovery-<完整用例名>.log`，批量与 relay 为 `temp/v0.7-recovery-batch.log`、`temp/v0.7-recovery-relay.log`。每份日志均实际运行一条测试，不以 0 条测试当通过。COMMIT 丢回包验证的是数据库提交后的网络确认窗口，Outbox 用例则在 AOF 确认后模拟旧租约过期，确实消费两条重复消息；没有强杀现有数据库。
