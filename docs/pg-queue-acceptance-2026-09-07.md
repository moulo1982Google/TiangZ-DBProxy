## 诊断证据与边界

Docker 的实际数据 VHD 位于本机机械硬盘；系统与工作区所在盘为 NVMe SSD。对 PG 数据卷使用 `pg_test_fsync -s 1` 的短时测量中，单次 8 KiB `fdatasync` 平均约 54.039 ms，`fsync` 约 133.983 ms。`synchronous_commit=on`、`fsync=on`、`wal_sync_method=fdatasync` 保持不变。该测量说明当前存储同步成本很高，尚未做 SSD 对照，不能证明它是所有游戏错误的唯一原因。

两轮失败必须区分：

- 冒烟服务端明确记录多次 PG 排队 2 秒超时及修复 ACK 排队失败。此前同一分片 16 个并发写入者、64 次保存的通过结果，不足以覆盖这次初始化峰值。
- 正式轮次的 DBProxy 日志没有相同排队超时。启动阶段相邻 PG 指标采样中，主节点队列均值约 106.133 ms、p99 在 (500, 1,000] ms 桶；PG operation 均值约 59.046 ms、p99 在 (250, 500] ms 桶。修复 ACK 的 p99 在 (1,000, 2,000] ms 桶。
- 失败现场的新进程累计 SDK 指标中，地图 1/100 连接队列均值约 1,605.910 / 2,161.193 ms，分别有 19/27 个样本超过 5 秒；这与客户端记录的约 5 秒 Actor RPC 超时同时出现。该数据是启动累计样本，不是稳定负载窗口，也不能与上述阶段 p99 相加。SDK 首次导出前没有可相减的标签序列，分析文件如实标记缺失基线。
- 两轮没有触发资源守卫，指标抓取没有失败。低频 CPU/内存采样不能排除局部瞬时争用。没有使用增加超时、增加连接、关闭持久化或忽略健康错误的方式取得通过结果。
