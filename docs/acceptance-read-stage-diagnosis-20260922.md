# 读取尖峰分段定位（2026-09-22）

后续[压测定时定位](acceptance-pacing-diagnosis-20260922.md)已单独复现压测程序等待迟到，并给出可选修正的真实读写对照；以下保留本轮原始结论。

本轮补齐计时并完成四轮 Docker 短测。80,000 个计划请求全部得到正确响应，40,000 次写入逐条读回一致；没有漏发、响应错误或诊断事件丢失。但是上一轮 T/U 的上百毫秒尖峰没有复现，不能宣布已经修复，也没有开始两小时验收。

前置结论及原始失败见[读取池实施验证](acceptance-read-pool-20260922.md)。本轮没有更改同记录请求顺序、并发上限或读写一致性规则。

## 现在可以区分什么

- 压测程序：计划发送到实际开始调用 SDK 的等待；SDK 发送排队和请求往返分别记录。
- DP：收到并解析请求后到任务开始运行、等待同记录前序请求、实际处理请求三个阶段分别记录。
- 存储：取得读取连接的等待，以及取得连接后的读取、写入耗时分别记录；保留原有合计指标。

DP 分段数据通过 `DbProxyMetrics::request_stage_snapshot()` 获取，由测试 host 写入 `storage-stages.jsonl`，尚未添加到 Prometheus 输出。固定 15 类操作、3 个阶段，不记录业务键。快照累计且不清零，只统计已完成阶段；并发读取各原子字段不是事务快照。任务调度计时不覆盖收包和解析之前的等待，处理计时不覆盖响应发送和客户端接收。

PG 读取/写入耗时包含客户端通信、重连与解码，不等于 PG 服务端纯 SQL 执行时间。它们是原有 `postgres_operation` 的细分，不能再与合计相加。不同请求的最大值也不能相加来还原一次请求。

SDK 诊断回调使用有界非阻塞通道，测试结束并完成数据核对后才写文件；事件丢失会让测试失败。W/X/Y 容量为 32,768，Z 扩至 65,536；实际事件分别为 21,001、21,001、21,001、57,001，均未丢失。这个缓冲方案只适合当前短测，两小时运行前必须改为有界持续排出并检查观察开销。增加计时本身也可能改变调度，未复现不等于消除原故障。

## 环境与结果

PG 18.6：4 CPU / 8 GiB、shared_buffers 2 GiB、max_connections 30，持久化设置保持开启；可靠 Redis 和独立缓存 Redis 均为 8.8.1。Docker 项目 `dp-acceptance-20260922`。所有测试均使用新建测试库，无旧库升级。

每秒 200 请求、最多 32 个在途请求，1 KiB 数据，读写各半。SDK `split4`，PG 4 写连接 + 2 读连接；清理开启，PG 记录至少 20 ms 的 SQL。DP 4 个运行线程、压测程序 32 个。读取固定不可变记录，写入各自不同的记录。每轮先预热 10 秒。

| 运行末尾编号 | 测量时长 | 类型 | 计划请求（含预热） | 漏发/错误/读回不符 | 核对写入 | 读取最大耗时 | 写入最大耗时 |
|---|---:|---|---:|---|---:|---:|---:|
| W | 60 秒 | 自然运行 | 14,000 | 0 / 0 / 0 | 7,000 | 24.655 ms | 39.028 ms |
| X | 60 秒 | 自然运行 | 14,000 | 0 / 0 / 0 | 7,000 | 22.226 ms | 56.318 ms |
| Y | 60 秒 | 自然运行 | 14,000 | 0 / 0 / 0 | 7,000 | 24.571 ms | 40.495 ms |
| Z | 180 秒 | 主动执行两次 CHECKPOINT | 38,000 | 0 / 0 / 0 | 19,000 | 27.125 ms | 41.306 ms |

表中读取/写入耗时从计划发送时间起算，限正式测量窗口；不是单条 SQL 耗时。独立账本检查确认：请求编号无重复、无缺失，响应与发送一一对应，每个成功写入都有且仅有一次读回核对。

### 本轮的慢读取主要慢在哪里

下表取每轮正式窗口中**同一条最慢读取**分解，不使用不同请求的百分位相减。

| 运行 | 请求编号 | 总耗时 | 开始调用 SDK 前等待 | 调用 SDK 后耗时 |
|---|---:|---:|---:|---:|
| W | 6093 | 24.655 ms | 22.743 ms | 1.912 ms |
| X | 5323 | 22.226 ms | 20.423 ms | 1.803 ms |
| Y | 10159 | 24.571 ms | 22.579 ms | 1.992 ms |
| Z | 4139 | 27.125 ms | 24.652 ms | 2.473 ms |

因此，这四条慢读取的大部分时间发生在压测程序开始调用 SDK 之前。尚未区分操作系统唤醒、运行线程调度和日志开销，不能直接归因于 Windows 定时器，也不能借此解释上一轮尚未重现的 T/U 尖峰。

全程累计分段数据（包含预热和读回核对）还显示：

- SDK 发送排队最大依次 0.096 / 0.102 / 0.108 / 0.125 ms。
- PG 读池等待全部在不超过 1 ms 的桶中；读取执行全部不超过 10 ms。
- DP 读取任务调度最大 0.818 ms；同记录顺序等待最大 5.512 ms；读取处理最大 6.713 ms。
- X 的写入处理最大 47.312 ms，PG 日志有 2 次慢 COMMIT，最大 33.745 ms；Z 有 4 次，最大 25.215 ms。这里是分别统计，未作逐请求因果匹配。

本轮没有读连接耗尽的证据。同记录读取仍按现有契约排队，这是潜在的放大路径；目前只有机制和计时验证，没有证据证明它造成之前的偶发尖峰，未修改该顺序保证。
