# 相同客户端连接数与受控写入阻塞（2026-09-22）

本轮承接[客户端读写分离短测](acceptance-client-split-20260922.md)，比较共用 8 条与读写各 4 条。正式 SDK、生产服务实现未修改；仅扩展诊断工具、集成测试及文档。

结论：两种配置均有自然负载失败轮。现有客户端分离并不能消除同 PG 请求连接上的读取等待；受控屏障进一步证明该机制。下一步应在正式存储连接层设计有数量限制的读写隔离，并覆盖全部相关读取路径，而不是继续仅增加客户端连接数。尚未实施该生产改动或启动两小时验收。

## 自然负载对照

沿用 PG 18.6、4 CPU / 8 GiB、Redis 8.8.1 的隔离 Docker 环境；每轮从当前 schema 新建库，预置 10 万近期和 10 万过期回执。4 个共用 PG 请求分片、清理开启、服务线程 4、发压线程 32、在途上限 32。每秒 200 请求，10 秒预热加 60 秒采样，1 KiB，固定热点读取与不同键新建写入各半。PG 独立读取诊断开关关闭。

| 目录后缀 | 客户端连接 | 漏发 | 最慢读取 ms | 读取调用 p99 ms | 核对写入 | 日志最慢 COMMIT ms |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| o | 共用 8 条 | 33 | 405.910 | 217.381 | 6,985 正确 | 94.585 |
| p | 读写各 4 条 | 24 | 357.751 | 59.365 | 6,987 正确 | 124.672 |
| q | 读写各 4 条 | 0 | 28.463 | 8.297 | 7,000 正确 | 未记录 ≥20 ms |
| r | 共用 8 条 | 0 | 27.344 | 7.879 | 7,000 正确 | 未记录 ≥20 ms |

最慢读取为采样端到端耗时；读取调用 p99 按每条请求减去自身发送等待后重新排序计算。O/P 各记录 16/12 条超过 20 ms 的 COMMIT。自然出现的尖峰并不相同，因此不能用 33 对 24 宣称固定比例的改善。Q/R 的单轮成功也不能覆盖 O/P 的失败。

合计计划 56,000 次请求，55,943 次收到正确响应，57 次因在途满而未发送；27,972 次写入读回内容和 revision 均正确，不含每轮一条初始化记录。独立日志审计验证计划编号完整覆盖、intent/response 一一对应、核对无遗漏或重复。数据库快照及回执行数均为本轮写入数加一。近期夹具回执各 100,000 条不变；过期回执剩 59,500 或 60,500 条，清理持续推进。

`acceptance_load` 新增 `shared8` 调用现有 `connect(config,8)`；脚本的 `-ClientConnections` 同步支持它。四轮使用相同 release 二进制且计时期间没有其他编译或测试。原始证据在 `target/probe_20260922o` 至 `target/probe_20260922r`；汇总和驱动在 `target/sdk_equal_20260922/{run.ps1,run.log,audit.py,audited-results.json,database-counts.json}`。失败轮保留失败状态。

复测参数与前次一致，分别设置新的 RunId 及 `-ClientConnections shared8` / `split4`：`-Rate 200 -Seconds 60 -WarmupSeconds 10 -Rounds 1 -CleanupMode on -HostWorkers 4 -LoadWorkers 32 -SqlLogThresholdMs 20 -ReadConnection shared`。不把本次单一操作组合称为完整生产负载。

## 受控阻塞：区分记录锁和连接等待

新增真实 SDK → TCP → 正式 StorageBackend → Docker PG/Redis 的测试 `eight_tcp_connections_do_not_isolate_reads_on_the_same_pg_shard`。PG 请求分片保持 4 个，客户端两种配置均为 8 条 TCP 连接，各重复 3 次，顺序交错。没有暂停 PG，没有修改持久化参数。

测试使用独立新库，触发器只让指定命名空间的一笔写入等待 advisory lock。先通过 `pg_stat_activity` 确认写入已经到达屏障，再发读取：

1. 读取另一条已提交记录，但与阻塞写入使用同一个 PG 请求分片：两种客户端配置都超过 150 ms 仍未返回。
2. 读取其他 PG 请求分片上的记录：两种配置均在写入仍阻塞时正确返回。
3. 用独立 PG 连接读取步骤 1 的同一条记录：正确返回，排除该记录本身被锁住或不可见。
4. 释放写入屏障：写入成功、等待的读取返回正确内容和版本，移除测试触发器和函数。

为避免把 TCP 等待错认成 PG 等待，测试按当前 SDK/服务端的 FNV 路由选择键：写入 hash % 8 = 0；同 PG 读取 = 4；其他 PG 读取 = 1。共用 8 条时这三个请求本来就在不同 TCP 连接上，前两个仍落在同一 PG 分片。路由算法若变更，必须同步更新该测试夹具，不能将它当成公共协议保证。

六次结果一致：同 PG 分片读取等待，其他 PG 分片和独立 PG 读取正常，释放后数据正确。旧的直接后端阻塞测试也通过；两个真实集成测试合计 2.25 秒。此屏障证明连接排队机制，不模拟磁盘落盘延迟，也不能给出生产容量或所有业务接口的结论。

复测使用新测试库、`DBPROXY_TEST_ALLOW_SCHEMA_MIGRATION=1`、显式测试 PG/Redis URL：

```powershell
cargo test -p tiangz-dbproxy-server --test read_write_contention --locked -- --ignored --nocapture --test-threads=1
```

证据位于 `target/sdk_equal_20260922/barrier.log`；测试库为 `probe_sdk_barrier_20260922`。新增用例只在显式 `--ignored` 时运行，日常 workspace 通过数量不包含它。

PG 写提交为何出现偶发长尾尚未定位到物理原因，不能归咎于某一磁盘、Docker 或 Windows，也不能通过关闭同步落盘来掩盖。可处理的已证实问题是写入占用连接时对读取的排队放大。正式改动须核查普通/批量权威读取、缓存回源、各类回执及交易读取，维持主库已提交读取语义，同时计算每租户、多实例的连接总量及维护连接，保持在 PG 限额内；不得直接复制只覆盖单条读取的诊断适配器。
