# 第二批索引与查询验证（2026-09-22）

本轮落实批量快照读取和两个队列的到期筛选改写，复用已有索引，没有新增索引或迁移。使用已获授权的 PostgreSQL 18.6 / Redis 8.8.1 Docker 环境。

## 修改与语义

- 批量快照原来的 `IN (unnest(...))` 在本次十万条数据、30/64 个参数时选择全分区扫描。改为 `unnest` 加逐键 LATERAL 查询，每个完整主键 `LIMIT 1`，使逐键索引查找保留在计划中。完整主键本来就最多匹配一条；仍是单条 SQL 的一致视图，Rust 层继续按输入顺序组装结果并保留缺失位置。服务端原有重复键拒绝规则不变。
- 缓存修复和 Outbox 的 `available_at` 上界由 `clock_timestamp()` 改为 `statement_timestamp()`，数据库可以把本条语句固定的到期时间用作已有日期索引的范围条件。
- **到期边界现在是本条领取语句开始时。** 执行过程中才到期的任务留给下一轮，不会提前领取。没有使用事务开始时间 `NOW()`，长事务中已经到期的任务仍可在后续语句领取。
- 租约失效检查、新租约截止时间仍使用 `clock_timestamp()`；没有改变领取排序、死信排除、Outbox 同组前序阻塞、publisher 过滤或 `SKIP LOCKED`。
- 三条生产 SQL 拆成独立 `.sql` 文件并以 `include_str!` 引用，查询计划测试直接读取这些文件；旧 SQL 只用于同数据对照。

## 数据与实测

PG 容器限额 1 GiB、shared_buffers 128 MB、work_mem 2 MB、max_connections 30、JIT 关闭；Redis AOF 开启。Rust 测试程序在 Windows 主机运行，连接 Linux 数据库容器。

快照样本是一个 namespace 下十万条记录，每条 payload 128 字节；按完整键查找 1、30、64 条。队列每种分布为 100,001 条：全部可领取；十万条延后一小时、仅最后一条可领取；十万条有有效租约；缓存修复十万条死信；Outbox 一千组的首条为死信、九万九千条后序被阻塞，另有一个可推进组。

执行参数化 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`，不禁用顺序扫描。每次领取用保存点回滚；每种队列分布整体回滚后执行 VACUUM/ANALYZE，避免回滚死行污染下一种分布。以下为最终验收日志的单次样本，共享页访问含缓存命中，不等同于磁盘读取量；不能据此推算稳定吞吐。

| 查询与分布 | 修改前 / 后共享页访问 | 修改前 / 后耗时 ms |
| --- | --- | --- |
| 快照 1 条 | 3 / 3 | 0.08 / 0.07 |
| 快照 30 条 | 2,643 / 90 | 18.75 / 0.24 |
| 快照 64 条 | 2,643 / 192 | 17.75 / 0.34 |
| 缓存修复全部可领取 | 1,247 / 1,242 | 19.08 / 17.33 |
| 缓存修复大量延后 | 1,233 / 11 | 6.92 / 0.04 |
| 缓存修复大量已租用 | 1,332 / 1,332 | 9.18 / 8.26 |
| 缓存修复大量死信 | 10 / 10 | 0.07 / 0.04 |
| Outbox 全部可领取 | 4,691 / 4,661 | 91.36 / 82.26 |
| Outbox 大量延后 | 4,661 / 15 | 27.25 / 0.07 |
| Outbox 大量已租用 | 4,889 / 4,889 | 27.89 / 24.77 |
| Outbox 死信头阻塞 | 4,663 / 4,663 | 371.44 / 377.22 |

批量读取和大量延后任务的访问量明确降低。**全部可领取、大量有效租约、Outbox 死信头阻塞的扫描/排序成本尚未解决。** 死信样本的页访问量没有改善，单次耗时小幅波动不作为性能收益；本轮没有恢复此前已证明会退化的 enqueue_order 单列索引。

## 检查与复现

新增 `query_plans` 三项测试通过：批量计划及实际存储 API 的顺序/缺失/payload；队列八种分布及指定 publisher；长事务内的到期边界、未到期及有效租约排除。对批量读取和大量延后任务设置宽松的实际页访问上限，不用机器相关的毫秒阈值判定通过。该测试已接入每次提交的 CI，在单独数据库执行。

原有真实依赖测试 35 项重新通过：索引专项 3、存储 22、缓存修复并发 8、网络 2；加上本轮 3 项，共 38 项。Rust 工作区 188 项、Clippy、格式、TypeScript SDK 21 项、CI 工作流静态检查和差异空白检查通过。SDK 测试调用了现有协议指纹生成器，没有产生协议或生成文件差异。

首次探测失败原因是测试代码用 `as_u64()` 读取 PG 18 输出为 `1.0` 的实际行数，得到 None。已改用兼容整数/小数的 `as_f64()`，保留实际行数断言并重跑通过；不是数据库查询失败，没有跳过断言。首次失败日志 `initial.log` 保留。
