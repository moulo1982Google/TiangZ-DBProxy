# P05：回执清理开与关的业务影响对照（2026-09-23）

结论：**通过。** 在每秒 200 请求下，开启回执清理（B2）与关闭清理（B1）相比，吞吐不变，读写 P99 的差别都在 ±6% 以内（绝对值不到 0.25 ms），远低于计划的暂定门槛（吞吐下降不超过 10%、P99 上升不超过 20%）。即使清理在整个测量期间满负荷删除过期回执，业务延迟也看不出差别。全部 12 轮零错误、零漏发。

## 做法

- 环境：服务器容器（同 [P08](acceptance-p08-2h-20260923.md)），PG 18.6 四核八 GB，全部生产后台任务开启（`--background all`），回执保留期 24 小时。代码为分支 `acceptance/index-retention-p08-20260923` 上的提交。
- 负载：每秒 200 请求，1 KiB，读写各半，32 在途，std 定时，读池 4 写 + 2 读，SDK split4。
- 每轮预热 2 分钟、测量 5 分钟；B1、B2 交替各跑 3 轮（关开、开关、关开），每轮用模板克隆的全新数据库。
- 两个场景：
  - `p05_a_none`：没有过期回执，另有 10 万条近期回执。清理任务运行但基本空闲。
  - `p05_a_large`：30 万条过期回执，另有 10 万条近期回执。开启清理的每轮在测量期间一直满批删除，每轮删掉约 22.4 万条、剩 7.6 万条，速度约每秒 480 条。
- 工具：`deploy/remote-test/run_p05.sh` 调用 `run_receipt_probe.sh --cleanup both --rounds 3`，`tools/analyze_p05.mjs` 逐轮统计并按模式取中位数。

## 结果

每个模式取 3 轮的中位数；最大值取 3 轮中的最大。

| 场景 | 模式 | 成功/秒 | 读 P50 / P99 / 最大 | 写 P50 / P99 / 最大 | 错误 / 漏发 |
|---|---|---:|---|---|---:|
| 无过期回执 | B1 清理关 | 200 | 3.60 / 3.94 / 5.40 ms | 4.52 / 5.08 / 19.2 ms | 0 / 0 |
| 无过期回执 | B2 清理开 | 200 | 3.60 / 4.17 / 5.30 ms | 4.50 / 5.09 / 21.5 ms | 0 / 0 |
| 30 万过期 | B1 清理关 | 200 | 3.60 / 4.27 / 6.01 ms | 4.54 / 5.16 / 13.1 ms | 0 / 0 |
| 30 万过期 | B2 清理开 | 200 | 3.60 / 4.17 / 6.01 ms | 4.51 / 5.13 / 9.8 ms | 0 / 0 |

| 场景 | 吞吐变化 | 读 P99 变化 | 写 P99 变化 | 判定 |
|---|---:|---:|---:|---|
| 无过期回执 | 0% | +5.8%（+0.23 ms） | +0.1% | 通过 |
| 30 万过期 | 0% | −2.3% | −0.6% | 通过 |

- 读 P99 的轮间波动本身就有约 0.4 ms（3.88–4.34 ms），+0.23 ms 在噪声范围内；有积压的场景里 B2 反而略低，也说明没有可测出的影响。
- 写入最大值在两种模式下都偶发 10–20 ms，与[尖峰定位](acceptance-spike-localization-20260923.md)一致，来自 PG 的 WAL 与检查点，与清理无关。
- 每轮 PG 日志中 20 ms 以上的语句只有 2 条，都是轮末的回执计数核对查询，不属于业务流量。

## 与计划的差异与边界

- 计划要求先测 B1 的稳定承载能力，再按其 50%、75% 的速率对照。本轮只在已验证稳定的每秒 200 请求下对照，没有做承载能力阶梯测试，也没有覆盖接近饱和时的影响。这一点单列为后续项。
- 负载只有普通读写，不含事务、批量、Outbox 事件。
- 清理的默认节奏是满批后暂停 1 秒、否则 60 秒，结论只针对这一节奏。
- 单实例单租户；多实例同时清理同一库的影响属于 P09。
